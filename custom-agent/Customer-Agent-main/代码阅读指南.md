# 代码阅读指南 —— 按框架分层逐步理解

## 阅读顺序总览

```
第1步  启动入口      app.py → config.py          理解系统如何初始化
第2步  桥梁层        bridge/                     理解消息如何在各层之间流通
第3步  消息系统      Message/                    理解消息队列 + 处理器链
第4步  智能体层      Agent/                      理解 AI 如何生成回复
第5步  渠道层        Channel/                    理解外部平台如何接入
第6步  数据库层      database/                   理解知识库和账号存储
第7步  UI 层         ui/                         理解桌面界面如何串联一切
第8步  核心设施      core/ + utils/              理解 DI 容器、日志等基础设施
```

---

## 第 1 步：启动入口（2 个文件，10 分钟）

### 按顺序读：

**`app.py`**（96 行）
- 关注点：启动时按什么顺序初始化全局单例
- 第 29-43 行的注释就是初始化链路：`config → db_manager → logger → DI容器`
- `main()` 函数只看 65-93 行，就是创建 QApplication → MainWindow → exec()

**`config.py`**（416 行）
- 关注点：配置从哪来、有什么配置项、怎么读写
- 第 53-68 行 `ConfigModel`：系统所有配置的结构定义（LLM、Prompt、营业时间、DB路径）
- 第 72-92 行 `config_base`：默认配置值
- 第 116-150 行 `Config.__init__`：配置文件是 `config.json`，不存在就**自动创建**
- 第 380 行：`config = Config()` 全局单例

> **读完这两文件你应该理解**：应用启动 → 自动加载/创建 config.json → 注册服务到 DI 容器 → 打开主窗口

---

## 第 2 步：桥梁层（2 个文件，15 分钟）

### `bridge/context.py`
- `ChannelType` 枚举（第 7 行）：支持的平台列表
- `ContextType` 枚举（第 17 行）：消息类型（TEXT/IMAGE/GOODS_INQUIRY...）
- `Context` 类（第 34 行）：**整个系统流通的"消息信封"**，所有层都用它传递消息
- `PinduoduoKwargs`（第 60 行）：拼多多特有的字段（shop_id, user_id, from_uid...）

### `bridge/reply.py`
- `ReplyType` 枚举：回复类型（TEXT/IMAGE/LINK...）
- `Reply` 类：Bot 返回的回复容器，就 `type + content` 两个字段

> **核心概念**：`Context` 是消息从渠道流向 Agent 的载体，`Reply` 是 Agent 返回结果流向渠道的载体。整个系统就是 `Context → Handler → Bot.reply() → Reply`。

---

## 第 3 步：消息系统（8 个文件，30 分钟）

### 阅读顺序：

**`Message/message.py`** — `ChatMessage` 数据类，消息的最底层抽象（渠道原始消息转成这个）

**`Message/models/queue_models.py`** — `MessageWrapper`（队列里的消息包装器）、`QueueConfig`

**`Message/core/queue.py`** — `SimpleMessageQueue`（asyncio.Queue 封装）
- `put(context)` 放入消息
- `get(timeout)` 取出消息
- `queue_manager` 全局单例管理所有队列

**`Message/core/consumer.py`** — `MessageConsumer`
- `_consume_loop()` 循环从队列取消息
- `_process_message()` 遍历 handler 链处理
- 信号量控制并发数

**`Message/core/handlers.py`** — `MessageHandler` 抽象基类
- `can_handle(context)` — 判断是否处理
- `handle(context, metadata)` — 处理消息
- 是一个**责任链模式**

**`Message/handlers/base.py`** — `BaseHandler`，Handler 的通用基类（日志、消息记录）

**`Message/handlers/preprocessor.py`** — `MessagePreprocessor`，消息预处理（清理、提取）

**`Message/handlers/ai_handler.py`** — `AIReplyHandler`，**最核心的 Handler**
- `_get_ai_reply()` 调用 `bot.async_reply(query, context)`
- `_send_reply()` 调用渠道的发送 API
- 第 104 行硬编码了 PDD 的 SendMessage ⚠️

**`Message/handlers/keyword_handler.py`** — `KeywordDetectionHandler`
- 检测"转人工"等关键词 → 调 PDD API 转接
- 第 9 行也硬编码了 PDD 的 SendMessage ⚠️

**`Message/__init__.py`** — 模块入口，`handler_chain()` 函数组装处理器链

> **读完这层你应该理解**：渠道收消息 → 转 Context → put 队列 → Consumer 取出 → 遍历 Handler 链（关键词检测 → AI 回复 → 兜底）→ 调用渠道 API 发回复

---

## 第 4 步：智能体层（6 个核心文件，30 分钟）

### 阅读顺序：

**`Agent/bot.py`** — `Bot` 基类
- 只有 `reply()` 和 `async_reply()` 两个方法
- 所有 AI 引擎必须继承这个

**`Agent/CustomerAgent/custom/agent_config.py`** — `AgentConfig`
- Agent 的所有运行时参数（token_window, temperature, max_loops 等）
- `validate()` 检查 api_key 是否配置
- `load_from_config()` 从 config.json 读取

**`Agent/CustomerAgent/custom/llm_client.py`** — `LLMClient`
- 封装 OpenAI 兼容 SDK（`AsyncOpenAI`）
- `chat(messages)` 发送请求，返回 `LLMResponse`
- 第 104-121 行：支持 tool_calls

**`Agent/CustomerAgent/custom/message_builder.py`** — `MessageBuilder`
- 构建发给 LLM 的 messages 数组
- 组装 system prompt（instructions + 工具描述）+ 历史消息 + 用户query

**`Agent/CustomerAgent/custom/tool_executor.py`** — `ToolExecutor`
- `execute_parallel()` 并行执行多个工具调用
- 用线程池避免阻塞 asyncio 循环

**`Agent/CustomerAgent/custom/customer_agent.py`** — `CustomerAgent(Bot)`，**最核心**
- `initialize_async()` 初始化 LLMClient + SessionManager + 工具
- `_run_agent_loop()`（第 197-273 行）→ **Agent 核心循环**：

```
while loop_count < max_loops:
    1. LLMClient.chat(messages)      → 调 LLM
    2. 检查是否有 tool_calls         → 没有就返回答案
    3. 并行执行所有工具              → ToolExecutor.execute_parallel()
    4. 把工具结果追加到 messages     → 回传 LLM
    5. loop_count += 1               → 继续循环
```

**工具文件（`Agent/CustomerAgent/tools/`，了解即可）：**

| 文件 | LLM 工具名 | 作用 |
|------|-----------|------|
| `get_product_knowledge.py` | `get_product_knowledge` | 查产品知识库 |
| `search_customer_service_knowledge.py` | `search_customer_service_knowledge` | 搜索客服知识 |
| `get_product_list.py` | `get_shop_products` | 获取店铺商品列表 |
| `send_goods_link.py` | `send_goods_link` | 发商品卡片（PDD专属） |
| `move_conversation.py` | `transfer_conversation` | 转人工（PDD专属） |

**`Agent/CustomerAgent/custom/tool_decorator.py`** — 工具注册机制
- `@agent_tool` 装饰器注册工具到全局 `TOOL_REGISTRY`
- `get_tools_for_llm()` 转成 OpenAI 函数调用格式

> **读完这层你应该理解**：Agent 就是一个 while 循环——每次调 LLM，LLM 返回"我要调工具"或"这是最终回答"，循环直到 LLM 不再调工具。

## 第 5 步：渠道层（7 个核心文件，30 分钟）

### 阅读顺序：

**`Channel/channel.py`** — `Channel` 基类
- 生命周期方法：`start_account()` / `stop_account()` / `start_account_all()` / `stop_all()`
- shop CRUD：`add_shop()` / `remove_shop()`

**PDD 渠道核心链路（按调用顺序读）：**

**`Channel/pinduoduo/pdd_channel.py`** — `PDDChannel` 主类
- 第 1 行看类定义：通过 4 个 Mixin 组合而成
- `PDDChannel(ConnectionMixin, MessageHandlerMixin, LifecycleMixin, StatusMixin, Channel)`

**`Channel/pinduoduo/core/pdd_lifecycle.py`** — `LifecycleMixin`
- `start_account()` 启动入口 → 调 `init()`
- `init()` 获取 token → 建 WebSocket → 启动心跳/消息循环/健康检查协程
- `request_stop()` 设置停止信号

**`Channel/pinduoduo/core/pdd_connection.py`** — `ConnectionMixin`
- `_connect_with_retry()` WebSocket 连接 + 指数退避重连
- 连接地址是 `wss://m-ws.pinduoduo.com/`

**`Channel/pinduoduo/core/pdd_message_handler.py`** — `MessageHandlerMixin`
- `_process_websocket_message()` → 解析 JSON → 转 `PDDChatMessage`
- `_convert_to_context()` → 转成 `Context` 对象
- 分发逻辑：立即处理 vs 放入队列 vs 忽略

**`Channel/pinduoduo/pdd_message.py`** — `PDDChatMessage`
- 继承 `ChatMessage`，拼多多消息格式的解析器
- `MessageTypeHandler` 静态方法：判断消息类型

**`Channel/pinduoduo/utils/API/send_message.py`** — `SendMessage`
- 继承 `BaseRequest`，拼多多 HTTP API 的发送端
- `send_text()` / `send_mallGoodsCard()` / `move_conversation()` 等方法

**`Channel/pinduoduo/utils/base_request.py`** — `BaseRequest`
- 通用 HTTP 客户端：重试、cookie 管理、会话过期自动重登
- GET/POST 封装

> **读完这层你应该理解**：渠道 = 连接（WebSocket/HTTP）+ 消息解析（原始格式→Context）+ 消息发送（Reply→平台 API）。PDD 用 WebSocket 长连接 + cookie 认证，视频号需要改成 HTTP 轮询 + OAuth2 token。

## 第 6 步：数据库层（4 个文件，20 分钟）

### 阅读顺序：

**`database/models.py`** — SQLAlchemy ORM 模型
- `Channel` 表：渠道类型
- `Shop` 表：店铺信息
- `Account` 表：账号（含 cookies）
- `ProductKnowledge` 表：产品知识（goods_id, extracted_content...）
- `CustomerServiceKnowledge` 表：客服知识（title, content, tags...）
- `Keyword` 表：转人工关键词

**`database/db_manager.py`** — `DatabaseManager`
- 对 Channel/Shop/Account/Keyword 的 CRUD
- `_LazyDBProxy` 实现向后兼容

**`database/knowledge_service.py`** — `KnowledgeService`
- 产品知识 CRUD
- 客服知识 CRUD + 批量导入
- **`search_knowledge(shop_id, query)`**：用 jieba 分词做关键词匹配搜索

**`database/product_sync.py`** — `ProductSyncService`
- 从 PDD API 同步商品列表 → 存入本地数据库
- 用 LLM 提取商品知识（extracted_content 字段）

> **读完这层你应该理解**：知识库 = SQLite，两张核心表（产品知识 + 客服知识），用 jieba 分词搜索，Dify 改造后直接复用 `KnowledgeService.search_knowledge()`。

---

## 第 7 步：UI 层（5 个核心文件，30 分钟）

### 阅读顺序：

**`ui/main_ui.py`** — `MainWindow`
- 第 1 行看用了什么框架：PyQt6 + qfluentwidgets（Fluent Design 风格）
- 7 个标签页：自动回复 / 关键词 / 账号 / 知识库 / 联系我们 / 日志 / 设置
- 懒加载：`QTimer.singleShot(200, self.lazy_load_views)`

**`ui/auto_reply/` — 自动回复子系统（核心 UI 逻辑）**

- **`ui/auto_reply/manager.py`** — `AutoReplyManager` 全局管理器
  - `start_auto_reply(account)` → 创建线程
  - `stop_auto_reply(account)` → 停止线程
  - `stop_all()` → 窗口关闭时调用

- **`ui/auto_reply/threads.py`** — `AutoReplyThread(QThread)`
  - 每个账号一个独立线程
  - `run()` → 创建 asyncio 事件循环 → 创建 PDDChannel → `start_account()`
  - **第 67 行硬编码了 PDDChannel** ⚠️

- **`ui/auto_reply/card.py`** — `AutoReplyCard` 单个账号卡片
  - 显示店铺 logo + 名称 + 状态
  - 上线/离线/开始回复 按钮

- **`ui/auto_reply/ui.py`** — `AutoReplyUI` 面板容器
  - 刷新/启动全部/停止全部 按钮
  - 定时同步线程状态

**`ui/setting_ui.py`** — 设置页
- LLM 配置卡片（api_base, api_key, model_name）
- Prompt 配置卡片（行为指令）
- 营业时间卡片

**`ui/Knowledge_ui.py`** — 知识库管理页
- 产品知识 tab：同步/查看/编辑
- 客服知识 tab：添加/批量导入/标签筛选

**`ui/user_ui.py`** — 账号管理
- Channel/Shop/Account 的增删改查

> **读完这层你应该理解**：UI 通过 `AutoReplyManager` 管理多账号的生命周期，每个账号 = 一个 QThread + 一个 Channel 实例 + 一个 asyncio 事件循环。设置页的配置改动会立即写入 config.json。

## 第 8 步：核心设施（3 个文件，15 分钟）

**`core/di_container.py`** — 依赖注入容器
- 支持 SINGLETON / TRANSIENT / SCOPED 三种生命周期
- `configure_standard_services(config)` 注册所有服务
- `container.get(SomeClass)` 获取实例

**`core/connection_status.py`** — `ConnectionStatusManager`
- 全局单例，跟踪所有账号的连接状态
- 被 UI 查询显示状态指示灯

**`utils/logger_loguru.py`** — 日志系统
- 基于 loguru，文件滚动（10MB × 5 个备份）
- `UILogHandler` 把日志桥接到 Qt 信号，让 LogUI 实时显示

## 改造时重点关注的文件

如果要动手改成视频号 + Dify，以下 5 个文件是**必须改**的核心节点：

```
1. Channel/channel.py              ← 加 send_text()/transfer_to_human() 抽象方法
2. Message/handlers/ai_handler.py  ← 去掉第 104 行的 PDD import
3. Message/handlers/keyword_handler.py ← 去掉第 9 行的 PDD import
4. ui/auto_reply/threads.py       ← 去掉第 67 行的 PDDChannel 硬编码
5. bridge/context.py              ← 加 WechatVideoKwargs
```

加上 2 个**新建**的包：

```
6. Channel/wechat_video/  ← 视频号渠道实现（约 8 个文件）
7. Agent/DifyAgent/        ← Dify 智能体（约 3 个文件）
```
