# 多问题拆分 + 知识库增量更新 — 实施规格

> **来源**：grill 决策对齐（2026-07-27）
> **关联**：`智能客服优化方案规格.md`（阶段一～四）
> **状态**：ready-for-agent

---

## Problem Statement

当前系统存在两个未覆盖的能力缺口：

1. **多问题无法感知**：用户一口气问多个问题（"比亚迪宋多少钱？有没有现车？能试驾吗？"）时，系统整体送入 ChatClient，LLM 自由发挥。回答可能遗漏子问题、偏重某一问、或答非所问。技术方案框架 §5.2 已给出拆分→并行检索→合并回答的路线，但未实施。

2. **知识库无增量更新**：车源数据变更必须全量重建索引或重启后才生效。公司车源库通过 MQ 广播推送实时变更消息，但系统没有对接能力。此外，向量库平铺存储（一条 SKU = 一个 Document），缺少车系/车型的层级结构，无法表达车系级统计数据（销量、车型列表摘要）。

此外，热度计算仅依赖销量，缺少用户询问行为的信号——用户频繁问某款车本身就是热度指标，应该纳入排序。

---

## Solution

在 `CarSalesAgent.chat()` 主流程中插入多问题拆分，在知识库层引入父子文档结构和增量更新机制。

### 多问题拆分

```
chat(userId, message):
    1. 多问题检测 + 拆分（规则优先 + LLM 兜底）
    2. if 单问题 → 走现有流程（闲聊检查 → VagueQueryRouter → ChatClient）
    3. if 多问题 → 每个子问题串行走现有流程 → LLM 合并成自然回复
```

- 拆分后的子问题保持用户原始顺序，不做优先级重排
- 拆分后每个子问题独立通过闲聊检查（3 个闲聊子问题 = 计数 +3，直接触发终止）
- LLM 合并调用负责把 N 段子答案组织成一段自然回复，不做 B 方案（简单拼接）

### 知识库增量更新

**父子文档结构**：

| 层级 | 内容 | embedding | 更新触发 |
|------|------|-----------|---------|
| 子块（车型） | 完整 SKU 渲染（价格/配置/颜色/车商/备注） | ✅ | MQ 广播到达即更新 |
| 父块（车系） | 百科车系介绍 + 聚合销量 + 车型列表摘要 + 询问次数 | ✅ | 子块车型列表变更或销量变更时级联重建 |

- 父块按 `brand_name + series_name` 聚合
- 检索只返回子块，父块作为子块 metadata 引用的补充上下文（按需展开）
- 父块百科内容来自知识库百科文档（公司库中有该车系才建父块，没有的不建）
- 车源所有字段（含价格）都进向量库，不做实时 API 查价

**更新链路**：

```
公司车源DB变更 → MQ 广播（JSON）→ 系统接收 → 同步直写 Chroma
                                    │
                                    子块 增/删/改
                                    │
                                    级联检查父块（哈希对比）
                                    │
                                    车型列表变了 / 销量变了 → 重建父块
```

- MQ 消息格式待后续对接，本次定义接收接口（方法签名 + 数据结构），Mock 实现
- 启动时通过哈希对比做增量检查（对比 car_sku 行哈希和上次入库哈希）
- 提供手动触发接口 `POST /api/kb/sku/refresh`

**询问次数与时间衰退**：

每次 VagueQueryRouter 匹配到某车系时，该车系（父块级）的周询问次数 +1。

热度公式：`加权询问次数 + 销量`，其中加权询问次数按周分桶 + 时间衰减：

| 周 | 衰减系数 |
|----|---------|
| 本周 | 1.0 |
| 第1周（上周） | 0.8 |
| 第2周 | 0.6 |
| 第3周 | 0.4 |
| 第4周 | 0.25 |
| 第5周 | 0.15 |
| 第6周 | 0.08 |
| 第7周 | 0.03 |

询问次数数据结构：车系 × 每周累计数，窗口 8 周，超出窗口自动丢弃。

## User Stories

### 多问题拆分

1. 作为用户，当我说"比亚迪宋多少钱？有没有现车？能试驾吗？"时，我希望 AI 依次回答我的每一个问题，不遗漏也不偏重某一问。
2. 作为用户，当我说"太贵了，有没有便宜点的"时，系统应该先识别这是一个复合表达（情绪 + 新需求），拆开后让"有没有便宜点的"能独立检索到同级别低价车型。
3. 作为用户，当我说"20万有什么SUV推荐？省油一点的，最好是混动"时，系统应该将后续约束条件合并到推荐检索中，而不是每个条件单独答。
4. 作为用户，当我一口气问了3个闲聊问题（"天气好吗""吃了吗""你是谁"）时，系统应该触发闲聊终止，而不是以为我在讨论车。
5. 作为开发人员，当用户输入以标点（问号、换行）自然分隔多问题时，我希望系统用规则直接拆分（零 LLM 成本），而不是每次都调 LLM。
6. 作为开发人员，当规则无法拆分的口语化连珠炮（"比亚迪宋怎么样太贵了有没有便宜点的"）出现时，我希望系统回退到 LLM 拆分兜底。
7. 作为开发人员，多问题拆分后的子问题保持原始顺序，交给合并 LLM 组织叙事顺序，不在拆分阶段重排。

### 知识库增量更新

8. 作为系统运维人员，当公司车源数据库某款车的价格发生变化时，我希望 MQ 广播通知后，系统自动更新对应车型的向量，不需要重启服务。
9. 作为系统运维人员，当某车系下新增了一款车型，我希望系统自动更新该车系的父块（车型列表摘要），保持向量库和公司数据库一致。
10. 作为开发人员，当公司还没有某车系时，不希望生成该车系的父块——父块只对应公司在售车源。
11. 作为开发人员，检索时只返回车型子块，父块通过子块 metadata 的引用按需加载，避免父块的百科介绍直接出现在精确价格查询的结果中。
12. 作为开发人员，我希望系统启动时通过哈希对比识别变更的 SKU 行，只重建变化的向量，而不是全量删光重建。
13. 作为开发人员，我希望提供一个手动触发接口 `POST /api/kb/sku/refresh`，让运维人员可以在不需要重启的情况下手动触发车源向量同步。

### 询问次数与热度

14. 作为销售，当某款车被用户频繁询问时，我希望它在推荐排序中获得更高的热度权重，因为询问本身就是市场需求的信号。
15. 作为开发人员，当用户在对话中提到某车系并触发路由匹配时，系统应自动记录该车系的询问次数（父块级、按周分桶）。
16. 作为开发人员，计算热度时询问次数的贡献应随时间衰减——本周的询问比四周前的询问更有参考价值。
17. 作为开发人员，超过 8 周的询问数据自动丢弃，不再参与热度计算。

## Implementation Decisions

### 决策1：多问题拆分位置

`QuestionSplitter.split(message)` 在 `CarSalesAgent.chat()` 中、VagueQueryRouter 之前调用。返回 `List<String>`，单元素列表表示无需拆分，多元素表示需要串行处理。

### 决策2：两层检测机制

**Tier 1（规则）**：正则检测标点分隔符（`？`、`？`、`\n`、`；`），以及连接词（"还有""另外""顺便""同时"）。能切开的直接返回。

**Tier 2（LLM 兜底）**：规则无法切开时（返回单元素但疑似有多问题特征），调 LLM 结构化输出拆分。LLM 拆分时需完成指代消解——"太贵了"要变成"XX车型太贵了"+"有没有比XX便宜的替代车型"。

### 决策3：串行处理

子问题串行依次走 `闲聊检查 → VagueQueryRouter → ChatClient`。不并行——并行需要 ChatMemory 线程安全改造和 SQLite 连接池调整，当前阶段收益不足以覆盖改造成本。

### 决策4：LLM 合并

N 段子答案拼入合并 Prompt，一次 LLM 调用生成自然回复。Prompt 核心指令：

- 用一段自然的回复依次回答所有问题
- 相关的问题合并，不相关的自然过渡
- 不用"第1个问题""第2个问题"这种说法

### 决策5：父子文档存储

父块和子块存在同一个 Chroma collection 中，通过 metadata 字段区分：

- 子块：`type=车源`, `level=child`, `parent_series_id=<series_name>`
- 父块：`type=车源`, `level=parent`, `series_id=<series_name>`

子块 metadata 含 `parent_series_id`，检索命中子块后，LLM 可通过该字段查找父块获取车系级上下文。

### 决策6：父块渲染

父块由三部分拼接：
1. 百科车系介绍（从百科知识库按车系名匹配，无匹配则跳过）
2. 聚合统计（该车系下车型数量、能源类型覆盖、价格区间、可选颜色列表）——SQL 聚合，零 LLM 成本
3. 加权询问次数（从按周分桶数据计算）

### 决策7：子块渲染

保持现有 `CarSkuVectorIndexer.render()` 逻辑不变——所有字段（含价格、库存）都在子块中使用。MQ 更新时重新渲染变更的行。

### 决策8：MQ 广播接收

定义接口 `SkuChangeListener`：

```
interface SkuChangeListener {
    void onSkuChanged(SkuChangeEvent event);
}

SkuChangeEvent {
    Long skuId;
    ChangeType type;      // INSERT / UPDATE / DELETE
    Map<String, Object> changedFields;  // 变更字段（全量行或增量字段，取决于消息格式）
}
```

首次实现用 Mock（手动触发接口模拟消息），MQ 具体格式后续对接。

### 决策9：同步直写

MQ 消息处理线程中同步执行：定位子块 → 删除旧向量（按 `sku_id` metadata filter）→ 渲染写入新向量 → 哈希对比检查父块是否需要重建。不攒批。

### 决策10：启动时哈希增量

启动时从 `car_sku` 表读全量 → 逐行算哈希 → 和上次入库哈希（存于 `vector_sync_log` 表或 Chroma metadata）对比 → 只重建变化的行。全量哈希对比在 47 条规模下几乎零成本。

### 决策11：询问次数记录

VagueQueryRouter 路由匹配到车系名时，调用 `AskCountTracker.recordMention(seriesName)` 记录。存储结构按周分桶：

```
series_ask_count {
    "比亚迪-宋PLUS": {
        "2026-W30": 12,   // 本周
        "2026-W29": 18,   // 上周，系数 0.8
        "2026-W28": 8,    // 系数 0.6
        ...
    }
}
```

热度 = 销量 + Σ(每周询问次数 × 该周衰减系数)。超过 8 周的数据丢弃。

### 决策12：新增组件清单

| 组件 | 类型 | 职责 |
|------|------|------|
| `QuestionSplitter` | 接口 + 实现 | 规则/LLM 多问题检测拆分 |
| `AnswerMerger` | 组件 | LLM 合并多段子答案为自然回复 |
| `SkuChangeListener` | 接口 | 接收 MQ 车源变更（首次 Mock） |
| `SkuVectorUpdater` | 组件 | 单条 SKU 增/删/改的 Chroma 操作 |
| `SeriesParentBuilder` | 组件 | 父块渲染（百科 + 聚合 + 热度） |
| `AskCountTracker` | 接口 + 实现 | 按周分桶记录询问次数 + 时间衰退计算 |

## Testing Decisions

### 测试原则

- 只测试外部可观察行为，不测试内部实现细节
- Mock 外部依赖（VectorStore、LLM 调用、JdbcTemplate、MQ 消息）
- 使用 Spring Boot Test + JUnit 5 + Mockito

### 测试模块

| 模块 | 测试方法 | 关键场景 |
|------|---------|---------|
| QuestionSplitter（规则路径） | 单元测试 | "多少钱？有没有现车？"→ 2个子问题；单问题不拆分；闲聊连珠炮→规则无法拆分 |
| QuestionSplitter（LLM 路径） | 单元 + Mock | "太贵了有没有便宜点的"→ 拆分 + 指代消解 |
| AnswerMerger | 单元 + Mock LLM | 3段子答案合并为自然段落；不含"第X个问题"标记 |
| SkuVectorUpdater | 集成测试 | 改一条价格 → 旧向量删除 + 新向量写入 → 其他向量不受影响 |
| SeriesParentBuilder | 单元测试 | 新增车型 → 父块车型列表摘要更新；价格变更 → 父块不重建 |
| AskCountTracker | 单元测试 | 记录3次询问 + 2周衰减 → 加权得分正确；8周旧数据自动丢弃 |
| CarSalesAgent（多问题链路） | 集成测试 | 闲聊 ×3 → 触发终止；"比亚迪宋怎么样？多少钱？"→ 两条子答案合并 |
| 启动时哈希增量 | 集成测试 | 无变更 → 零向量更新；改2条 → 只更新2条 |
