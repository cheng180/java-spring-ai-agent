# AI幻觉防御实施规格

> **来源**：grill 决策对齐（2026-07-28）
> **关联**：`智能客服技术方案框架与流程设计.md` §6（三层防御原始方案）、`Spring AI智能客服设计方案.md` §7、`智能客服优化方案规格.md` 决策13（L2/L3 后移项 → 本规格提前落地）
> **状态**：ready-for-agent

---

## Problem Statement

当前智能客服（阶段0：Spring AI 2.0 + Chroma + SQLite + DeepSeek）的幻觉防御只有半套提示词约束，无任何生成后校验：

1. **报错价无人拦**：LLM 可能把 15.88 万说成 16 万、编造公司没有的车型并报价、报错门店电话——卖车场景里一次错误报价就是一次真实客诉。`CarSalesAgent.chat()` 拿到最终字符串就直接发给用户，中间没有任何对账机制。
2. **提示词规则不全**：框架文档规定的 5 条硬规则只落地了一半——缺「不知道就说不知道」「库存为 0 就说没货」「引用具体参数不模糊化」。
3. **校验缺少基准数据**：LLM 自主决策架构下，工具调用发生在 ChatClient 循环内部，代码拿不到工具返回的原始数据和 RAG 检索块，想做生成后校验也无处下手。

框架文档 §6 早已给出三层防御方案（L1 提示词 → L2 规则引擎 → L3 双模型），优化方案规格决策13 将 L2/L3 后移至「模糊路由上线后评估」；本规格在阶段0 代码基线上把三层 + 校验-修正闭环完整落地，不依赖任何未实施组件。

---

## Solution

```
用户消息 → CarSalesAgent.chat()
   │
   ├─ L1 提示词硬约束（补齐 5 条，零成本，全量必经）
   │
   ▼ LLM 生成（工具调用/RAG 检索在 ChatClient 内部完成，输出被双路同步捕获）
防御链（仅同步路径）：
   ├─ L2 规则校验：回答文本 vs 捕获基准（工具输出 + RAG 块），毫秒级，不调 AI
   │     ├─ 通过 → 输出
   │     ├─ 价格数字单一失配 / 含对冲词 → 自动修 → 重跑 L2 → 输出
   │     └─ 其余问题（编造车辆 / 品牌主张 / 门店信息错）→ L3
   ├─ L3 双模型审核（触发：购买意向词命中 或 L2 有残留问题）
   │     ├─ 无问题 / 给出修正 → 输出（原文或修正版）
   │     └─ 修不了 → 降级话术 + 结构化日志
   └─ 连续 2 轮被 L3 拒绝 → 企业微信接口直发销售账号（转人工）
```

全程产生结构化日志事件，为阶段7 幻觉率统计供数；流式路径 v1 仅 L1 保护。

核心设计原则（沿用设计方案 §7.6）：**能用代码规则检查的，不要用 AI；AI 验证只用于规则检查不了的语义层面。**

## User Stories

### L1 提示词补齐

1. 作为用户，当 AI 不知道答案时，我希望它直接说「这个我暂时不确定，我帮您确认一下～」，而不是猜测或类比其他车型。
2. 作为用户，当工具返回库存为 0 时，我希望 AI 直接说没货，而不是说「应该有」。
3. 作为用户，当知识库里有具体参数时，我希望 AI 引用具体数字，而不是模糊化处理。

### L2 规则校验

4. 作为销售，当 AI 报价与系统售价不一致时（15.88 万说成 16 万），我希望系统在发出前拦住并改正，避免客诉。
5. 作为用户，当 AI 提到一款公司没有的车并给出价格或「有现车」时，我希望系统识别为编造并拦截。
6. 作为用户，当 AI 给我门店电话/地址时，我希望每一个字都和门店表一致——错一个数字我可能就白跑一趟。
7. 作为开发人员，品牌校验只在「带价格/有货主张」语境触发——AI 说「我们没有特斯拉」不应被误报。
8. 作为开发人员，价格校验按字段类型零容差（指导价/全款/金融价），任一捕获源（工具输出或 RAG 块文本）出现相同数字即放行。
9. 作为用户，我问「落地价大概多少」时，AI 的估算数字不被规则校验误伤（交 L3 语义审）。

### 校验-修正闭环

10. 作为开发人员，当回答只有一个价格数字失配且归属唯一时，系统自动替换数字 + 剥掉「大概/约/左右」，重跑 L2 放行——不多花一次 LLM 调用。
11. 作为用户，当幻觉无法自动修正时，系统用第二个模型审核并给出修正后的回答。
12. 作为用户，当第二个模型也修不了时，我收到降级话术「需要和门店同事确认」，而不是一条可能错误的信息。

### L3 双模型

13. 作为开发人员，只有购买意向词命中或 L2 有残留问题时才调 L3，控制 token 成本和延迟。
14. 作为开发人员，L3 默认用 DeepSeek 低温（0.1）自审；ANTHROPIC_API_KEY 配好后改一行配置切换为 Claude 真双厂商。

### 转人工

15. 作为销售，当某用户连续 2 轮回答被 L3 拒绝时，我收到企业微信消息，可以介入接管该会话。

### 基准数据捕获

16. 作为开发人员，工具每次调用的输出被写入请求级持有器，校验器拿到的是「LLM 当时实际看到的数据」，而不是重新查询的结果。
17. 作为开发人员，RAG 检索块被自定义 Advisor 捕获——即使用户追问时 LLM 没调工具、凭对话记忆报价，车源文本块仍可作为比对基准。

### 日志与流式

18. 作为开发人员，每次防御动作产生一条结构化日志事件（层级/校验类型/严重度/处置/耗时），可按天聚合幻觉拦截率。
19. 作为开发人员，v1 流式路径仅 L1 保护，代码留 TODO；前端启用流式时再决策防御方案。

## Implementation Decisions

### 决策1：防御链接入点（同步单一收口）

防御链挂在 `CarSalesAgent.chat()` 的 `.call().content()` 之后、return 之前——同步路径唯一出口，所有校验/修正/降级都在这一个收口完成。`chatStream()` 不接防御链（见决策12）。

### 决策2：双路源头捕获（基准数据）

- **工具输出**：新增请求级持有器 `SourceCapture`。`chat()` 开始时清空 → `CarSalesTools` 三个方法返回前写入自身输出 → 防御链读取 → 请求结束清理。持有器按请求隔离（ThreadLocal 或请求作用域 bean）。
- **RAG 检索块**：新增自定义 Advisor `RagCaptureAdvisor`，排在 QuestionAnswerAdvisor 之后，从 advisor context 读取 `qa_retrieved_documents` 写入 SourceCapture。QuestionAnswerAdvisor 每轮都执行检索，因此即使用户追问时 LLM 凭对话记忆报价、没调工具，车源文本块（含价格）仍可作为比对基准。
- **捕获为空时**：对应校验跳过并记 debug 日志（如 LLM 凭记忆报门店电话而本轮未调 getStoreInfo）。这是已知边界，v2 可加 DB 兜底重查（见 Further Notes）。

### 决策3：L1 提示词补齐（5 条硬规则）

采用框架文档 §6.2 版本，写入 `PromptTemplates.systemPrompt()`：

```
## 严格规则（违反=严重错误）

1. 数据来源：只能使用工具查到的真实数据和知识库中的信息。
   绝不能编造任何价格、参数、库存、优惠、门店地址电话。
2. 价格严格：报价精确到知识库/工具返回的数字。
   知识库显示"全款23.33万"就说23.33万，不能说"大概23-24万"。
3. 不知道就说不知道：如果没有相关信息，直接说
   "这个我暂时不确定，我帮您确认一下～"
   不要猜测，不要类比其他车型。
4. 库存实事求是：工具返回库存为0就说没货，不要说"应该有"。
5. 知识库有具体参数就引用具体参数，不要模糊化处理。
```

**不含**旧设计方案 §7.3 的「禁止品牌对比」一条——更新的框架文档未收录它，且销售话术库本身含竞品对比话术，规则与知识库会打架。

### 决策4：L2 校验项与严重度（v1）

| 校验项 | 方法 | 严重度 | 处置 |
|--------|------|--------|------|
| 价格失配 | 正则提取价格主张 → 归属最近车型名 → 与捕获源三类价格字段（指导价/全款/金融价）精确比对 | MEDIUM | 单一失配 → 自动修；其余 → L3 |
| 价格对冲词 | 价格主张片段内含「大概/约/左右/差不多」 | MEDIUM | 剥词自动修 |
| 编造车辆 | 带价格或「有现车/有货」主张的车型不存在于任何捕获源 | HIGH | → L3 |
| 品牌/车系主张 | 品牌/车系带价格或有货主张但不在库；负向语境（没有/不卖/停售/对比）豁免 | HIGH | → L3 |
| 门店电话/地址 | 回答中的电话号/地址串与 getStoreInfo 捕获输出逐字比对 | HIGH | → L3 |
| 落地价等估算值 | 不做数字比对（DB 无比对字段） | — | 意向词命中时由 L3 语义审 |

价格主张提取正则（沿用框架文档）：`(\d+(\.\d+)?)\s*万`。

### 决策5：价格容差——分类型零容差

指导价/全款/金融价均为 DB 精确字段，**零容差**（仅允许两位小数浮点误差）。文档旧案的「偏差 >5% 才标记」作废——它与 L1「报价精确到数字」直接冲突：15.88 万说成 16 万（偏差 0.76%）在 5% 容差下会被放行，但这句话本身就是违规的模糊报价，v1 判 MEDIUM。

放行条件：价格主张的数字在**任一捕获源**（工具输出文本或 RAG 块文本）中出现即视为有据。

### 决策6：自动修限定条件

同时满足以下三条才自动修，任一不满足 → L3：

1. 失配价格数字唯一（全文只有一处失配）
2. 归属车型唯一（该数字只对应一款车）
3. 源价格字段唯一（该车的指导价/全款/金融价中只有一个能与主张语境对应）

自动修动作：替换该数字 token + 剥除该主张片段内的对冲词（大概/约/左右/差不多）→ 重跑 L2 → 通过则输出。例如「大概16万」→「15.88万」。

### 决策7：L3 触发器（v1）

满足任一即触发：

- **购买意向词命中**（用户消息）：我要订、订车、下单、签合同、定金、订金、今天提车、明天提车、全款买、按揭、贷款买。词表放配置项，可调。
- **L2 有残留问题**：决策6 自动修之外的全部问题。

**不触发项**：价格数字不单独触发（已被 L2 零容差确定性覆盖，L3 再审是浪费）；检索置信度触发留 v2（依赖捕获块 distance 元数据的可用性验证）。

### 决策8：L3 模型策略

- `DualModelVerifier` 注入独立的 ChatModel（接口可插拔），与主模型解耦。
- v1 默认实现：DeepSeek，`temperature=0.1` 低温自审——不依赖新 key，同分布随机错误可被低温复核压掉一部分。
- 配置项 `defense.reviewer.provider=deepseek|anthropic`；ANTHROPIC_API_KEY 配好后改配置即切换为 Claude 真双厂商（properties 中已配 `claude-sonnet-4-5`）。

### 决策9：L3 审核契约

审核 prompt 三项标准（沿用两份文档）：

1. 价格、参数必须与基准数据一致
2. 不能出现基准数据中没有的品牌/车型/门店信息
3. 不能有误导性表述（编造的优惠、不实的交付承诺）

输入：用户问题 + 捕获基准（工具输出 + RAG 块）+ 待审回答。结构化输出：

```
ReviewVerdict {
  has_issues: boolean
  issues: List<String>
  corrected_answer: String   // 有问题时给出；无法修正则为空
}
```

结果处置：

| 情形 | 动作 |
|------|------|
| has_issues=false | 输出原回答 |
| has_issues=true 且 corrected_answer 非空 | 输出修正版，日志记 L3_CORRECTED |
| has_issues=true 且 corrected_answer 为空 | 降级话术，日志记 DEGRADED，连续拒绝计数 +1 |
| L3 调用异常且有 L2 残留问题 | 降级话术（fail-closed），计数 +1 |
| L3 调用异常且仅意向词触发（无 L2 问题） | 放行原回答（fail-open），记 error 日志 |

### 决策10：降级与转人工

- 降级话术（沿用框架 §6.5）：「这个信息我需要和门店同事确认一下，稍后给您准确答复～」
- 连续拒绝计数：按 userId 计数（沿用 idleCounters 模式），L3 拒绝 +1，任一轮防御链全通过则清零；≥2 触发转人工。
- 转人工通道：**企业微信应用消息接口，直发销售的企业微信账号**（RPA 方案已弃用，不再走 pending_messages + pyautogui）。新增 `HumanHandoffNotifier` 接口 + 企微实现；企业微信应用凭证（corpid/secret/agentid）与销售账号映射为部署配置项。
- 通知内容：userId、最近一轮用户消息、L3 拒绝原因（issues 列表）、时间戳。

### 决策11：结构化日志事件

每次防御动作输出一条结构化日志（SLF4J + 参数化字段，便于后续采集）：

| 字段 | 说明 |
|------|------|
| timestamp | 事件时间 |
| userId | 会话标识 |
| layer | L2 / L3 |
| checkType | 校验类型（价格失配/编造车辆/门店信息/品牌主张/对冲词/语义审核） |
| severity | HIGH / MEDIUM / — |
| action | PASS / AUTO_FIXED / L3_TRIGGERED / L3_CORRECTED / DEGRADED / HANDOFF |
| detail | 具体差异（如「回答16万 vs 全款15.88万」） |
| latencyMs | 防御链耗时 |

按天统计、幻觉率 Dashboard 属阶段7 监控范围，不在本规格。

### 决策12：流式路径

v1 流式（`chatStream()` / `/api/chat/stream`）仅 L1 提示词保护，方法内留 TODO 注释。前端启用流式时按「缓冲→校验→一次性输出」或「流式照发+异步审计」另行决策。

### 决策13：新增组件清单与现有代码影响

新增组件（沿用阶段0 包结构风格）：

| 组件 | 类型 | 职责 |
|------|------|------|
| `agent/guard/SourceCapture.java` | 组件 | 请求级基准数据持有器（工具输出 + RAG 块） |
| `agent/guard/RagCaptureAdvisor.java` | Advisor | 捕获 QuestionAnswerAdvisor 的检索块写入 SourceCapture |
| `agent/guard/HallucinationDetector.java` | 组件 | L2 纯函数校验：回答文本 + 捕获基准 → HallucinationReport |
| `agent/guard/DefenseChain.java` | 组件 | 闭环编排：L2 → 自动修 → L3 → 降级 → 转人工计数 |
| `agent/guard/DualModelVerifier.java` | 组件 | L3 审核 + 修正（双模型接口，默认 DeepSeek 低温） |
| `agent/guard/HumanHandoffNotifier.java` | 接口 | 转人工通知点 |
| `agent/guard/WeComHandoffNotifier.java` | 实现 | 企业微信应用消息接口直发销售账号 |

`HallucinationReport` 数据结构（决策相关部分）：

```
HallucinationReport {
  issues: List<Issue>
}
Issue {
  checkType: enum      // PRICE_MISMATCH / HEDGED_PRICE / FABRICATED_CAR
                       // / BRAND_CLAIM / STORE_INFO_MISMATCH
  severity: enum       // HIGH / MEDIUM
  detail: String       // "回答报16万，捕获全款15.88万（比亚迪宋PLUS DM-i）"
  claimSpan: String    // 命中的主张片段（自动修定位用）
}
```

对现有代码的影响：

| 现有文件 | 影响 |
|---------|------|
| `CarSalesAgent.chat()` | `.call().content()` 之后接入 DefenseChain；开始/结束管理 SourceCapture 生命周期 |
| `CarSalesAgent.chatStream()` | 仅加 TODO 注释 |
| `CarSalesTools` 三个工具方法 | 返回前把输出写入 SourceCapture（每个方法加一行，沿用现有日志位置） |
| `PromptTemplates.systemPrompt()` | 补齐决策3 的 5 条规则 |
| `application.properties` | + reviewer 模型选择、意向词表、企微凭证等配置项 |

### 决策14：测试接缝（已与开发者对齐）

两条高位接缝，不再多开：

- **接缝 A（纯函数）**：`HallucinationDetector.verify(回答文本, 工具输出快照, RAG检索快照) → HallucinationReport`——零 Mock，覆盖全部校验规则矩阵。
- **接缝 B（链路）**：`CarSalesAgent.chat()`——Mock ChatModel 返回预设回答（含各类幻觉），L2/捕获/闭环全真实，HumanHandoffNotifier 用 Fake。断言最终输出文本 + 副作用（日志、通知、计数）。

L3 不单开缝——其触发与修正采纳都在接缝 B 覆盖；审核 prompt 的具体措辞不属于外部行为。

## Testing Decisions

### 测试原则

- 只测试外部可观察行为，不测试内部实现细节（正则写法、Advisor 排序等）
- Mock 外部依赖：ChatModel、VectorStore、JdbcTemplate、企微 HTTP 调用
- 栈：Spring Boot Test + JUnit 5 + Mockito（与前两份规格一致）
- 项目当前无测试代码，本规格建立首批测试

### 测试模块与策略

| 模块 | 接缝 | 关键场景 |
|------|------|---------|
| HallucinationDetector | A（纯函数） | 价格与捕获源精确一致 → PASS；16万 vs 15.88万 → MEDIUM（零容差，否定旧案5%）；「大概15.88万」→ MEDIUM 对冲词；报价车型不在捕获源 → HIGH；「我们没有特斯拉」→ 豁免不误报；「特斯拉25万有现车」→ HIGH 品牌主张；门店电话错一位 → HIGH；落地价估算数字 → 不校验；多车多价各自正确归属；捕获为空 → 跳过 + 日志 |

## Further Notes

### 与既有规格的关系

- `智能客服优化方案规格.md` 决策13 将 L2/L3 标为「模糊路由上线后评估必要性」→ 本规格将其提前，并把 L1/L2/L3/闭环作为一个完整体系落地。
- 本规格按阶段0 代码基线设计，不依赖三 Collection、原子事实、VagueQueryRouter 等未实施组件。未来这些组件上线后，L2 的实体存在性校验可升级为 entity_id 精确比对、参数校验可基于原子事实 metadata 实现（v2 方向）。
- 与 `多问题拆分与知识库增量更新-实施规格.md` 的联动：多问题拆分落地后，每个子问题的子回答独立过防御链，LLM 合并后的最终回复再过一次（以最终输出为准）。

### 转人工通道说明

优化方案决策12 弃用的是 RPA（pyautogui 图像识别）方案；转人工通知改走企业微信官方应用消息接口，直发销售的企业微信账号，无中间表、无 Python 侧组件。

### 成本与延迟估算

- L2：全量每轮执行，纯正则 + 字符串比对，<10ms。
- L3：仅意向词/残留触发，预估 <15% 对话轮次；默认 DeepSeek 低温单次调用，增加约 1-2s 延迟。
- 自动修：零 LLM 成本，覆盖最高频的价格小错场景。
