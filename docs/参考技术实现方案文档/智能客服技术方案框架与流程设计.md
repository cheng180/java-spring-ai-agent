### 3.2 分块策略：命题分块 + 父文档检索器

当前项目使用 `TokenTextSplitter(500)` 简单按token数切分，存在两个问题：
- 语义单元可能被从中间切断
- 小块检索命中后上下文不足

**目标方案：命题分块 (Proposition Chunking)**

```
原始文档
    │
    ▼
[1] LLM提取原子事实 (Atomic Facts)
    每条事实 = 一个独立、完整、可独立理解的陈述
    示例:
      文档原文: "比亚迪宋PLUS DM-i 2025款，指导价15.88万，纯电续航110km，
               亏电油耗4.5L/100km，搭载DM-i超级混动系统。"
      →
      事实1: 比亚迪宋PLUS DM-i 2025款指导价为15.88万元
      事实2: 比亚迪宋PLUS DM-i 纯电续航110km
      事实3: 比亚迪宋PLUS DM-i 亏电油耗4.5L/100km
      事实4: 比亚迪宋PLUS DM-i 搭载DM-i超级混动系统
    │
    ▼
[2] 事实聚类成Chunk
    语义相近的事实合并（如：同款车的参数合并为一个Chunk）
    每个Chunk ≈ 3-8条相关事实，约200-500字
    │
    ▼
[3] 父文档关联
    每个Chunk保留指向父文档的引用
    检索时先命中Chunk → 可选择性展开父文档获取完整上下文
    │
    ▼
[4] 元数据标注
    {
      source: "汽车百科知识库.md",
      type: "百科",
      brand: "比亚迪",
      series: "宋PLUS",
      model: "宋PLUS DM-i 2025款",
      category: "参数",
      chunk_id: "byd-songplus-003",
      parent_doc_id: "byd-songplus",
      created_at: "2026-07-24T10:00:00Z",
      doc_hash: "sha256:abc123..."
    }
```

**为什么不直接用TokenTextSplitter？**

| 维度 | TokenTextSplitter | 命题分块 |
|------|-------------------|---------|
| 语义完整性 | 可能在句子中间切断 | 保证每条事实完整 |
| 检索精度 | 噪声多（相邻chunk内容重叠但不精确） | 每条事实精确匹配 |
| 更新粒度 | 文档级（改了1句话也要重索引整篇） | 事实级（改了哪条更新哪条） |
| 幻觉控制 | LLM看到碎片化上下文，容易脑补 | 每条事实自包含，减少脑补空间 |
| 实现复杂度 | 低（一行代码） | 中（需LLM提取+聚类+映射） |

### 3.3 Embedding模型选型：BGE-M3

选择 **BGE-M3**（当前项目已在用），理由来自检索策略文档：

```
BGE-M3 统一了三种检索能力:

1. Dense Retrieval (稠密向量)
   1024维语义向量，用于语义相似度匹配
   → 用户问"省油的车"能匹配到"亏电油耗4.5L"

2. Sparse Retrieval (稀疏向量/词权重)
   类似BM25但带语义的词权重，每个词有一个权重分数
   → "比亚迪"权重高于"的/是/在"等停用词

3. Multi-Vector Retrieval (多向量/ColBERT风格)
   每个token生成独立向量，检索时token级交互匹配
   → "宋PLUS"与"宋 plus"、"宋plus"等变体精准匹配

一次embedding调用，同时产出三种向量，存入三个索引，
检索时三路并行 → RRF融合 → 互为补充。
```

**配置要点：**
- 当前用硅基流动的BGE-M3 API（OpenAI兼容端点）
- 后续考虑本地部署（Ollama加载BGE-M3，免除API费用和延迟）
- 注意：更换embedding模型必须清空全库重建索引

## 4. 检索策略方案

### 4.1 混合检索三路并行架构

```
用户Query: "二十来万的混动SUV有什么推荐"
    │
    ▼
┌──────────────────────────────────────────────────────┐
│                [0] Query预处理 (可选)                  │
│  · 查询改写: LLM扩展同义表达                            │
│    → ["20万左右混动SUV推荐", "20-25万插混/增程SUV"]    │
```

### 4.2 RRF vs 加权融合的选择

| 策略 | 公式 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| RRF | Σ 1/(k+rank) | 无需调参，各检索器天然可比 | 无法表达偏好（某些检索器更重要） | 初期快速落地 |
| 加权融合 | Σ w_i × score_i | 灵活调整各路权重 | 需要调参，分数需要归一化 | 有调优数据后 |

**推荐：先RRF快速上线 → 积累检索日志 → 分析各路贡献 → 调为加权融合。**

### 4.3 检索增强策略

| 策略 | 触发条件 | 做法 |
|------|---------|------|
| **多Query扩展** | 原始query检索结果相似度全部 < 0.5 | LLM生成2-3个改写query，分别检索后合并 |
| **对话上下文注入** | 检测到指代词("那款""这个""刚才说的") | 从对话历史提取最近提到的车型，拼入检索query |
| **Metadata过滤** | 明确知道检索范围 | `type == '百科'` 或 `brand == '比亚迪'` 缩小检索域 |
| **HyDE** | 用户query很短很模糊 | LLM先生成假设性答案 → 用答案做向量检索 → 替代直接用query |

## 5. 模糊语义与多问题处理

### 5.1 模糊语义处理：四维排序算法

**核心问题**：用户说"还有吗那款车"、"太贵了"、"感觉一般"，query中没有明确的品牌/车型关键词。

**根本原因**：
- 纯向量相似度：模糊表达与任何车辆文本的cosine similarity都低
- 纯关键词匹配：没有品牌名/车型名可匹配
- 缺少对话历史和业务上下文的利用

**解决方案：动态权重的四维排序**

```
最终得分 = α × 语义相似度 + β × 上下文关联 + γ × 热度权重 + δ × 关键词匹配

正常场景（语义相似度 ≥ 0.5）:
  α=0.40  β=0.25  γ=0.25  δ=0.10

模糊场景（语义相似度 < 0.5）:
  α=0.10  β=0.50  γ=0.35  δ=0.05
  → 大幅降低语义权重，提升上下文和热度权重

极端模糊（语义相似度 < 0.3 且 无上下文）:
  不排序，触发引导追问策略
```

**四维详解**：

| 维度 | 计算方法 | 数据来源 |
|------|---------|---------|
| **语义相似度** | BGE-M3稠密向量Cosine Similarity，归一化到[0,1] | Chroma向量库 |
| **上下文关联** | 对话历史中是否提到该车辆：提到=0.35，未提到=0 | ConversationManager提取车型 |
| **热度权重** | 该车在客户所在门店过去30天的(咨询量/最大咨询量)，归一化[0,1] | store_car_hot表 |
| **关键词匹配** | query中出现的品牌名/车型名加分：每命中一个+0.05，上限0.10 | 品牌/车型词库匹配 |

**兜底策略（触发条件：top1得分 < 0.3）**：

不是直接说"找不到"，而是LLM生成引导追问：
- "太贵了" → "您预算大概多少？我帮您找找更合适的"
- "还有吗" → "您上次看的是哪款车？我帮您看看类似的"
- "推荐一款" → "您更关注轿车还是SUV？主要通勤还是家用？"

### 5.2 多问题处理：拆分 → 并行检索 → 合并

### 6.3 L2: 规则引擎事实校验

```java
@Component
public class HallucinationDetector {

    /**
     * 校验LLM回答中的关键事实
     * 检查项：价格、品牌存在性、数值偏差、编造卖点
     */
    public HallucinationReport verify(String llmAnswer, String sourceKnowledge,
                                       List<CarInventory> toolResults) {

        HallucinationReport report = new HallucinationReport();

        // 1. 价格校验：提取回答中的所有价格数字 → 对比工具返回的实际价格
        List<PriceClaim> claims = extractPriceClaims(llmAnswer);
        // 正则: (\\d+(\\.\\d+)?)\\s*万
        for (PriceClaim claim : claims) {
            Optional<CarInventory> match = findCarInResults(claim.carName, toolResults);
            if (match.isEmpty()) {
                report.addIssue(Severity.HIGH, "编造车辆",
                    "回答提到「" + claim.carName + "」但工具未返回此车");
            } else if (Math.abs(claim.price - match.get().salePriceWan()) > 0.05 * match.get().salePriceWan()) {
                report.addIssue(Severity.MEDIUM, "价格错误",
                    "回答报" + claim.price + "万，实际全款" + match.get().salePriceWan() + "万");
            }
        }

        // 2. 品牌校验：回答中的品牌名是否全部在知识库/工具结果中出现过
        List<String> mentionedBrands = extractBrands(llmAnswer);
        Set<String> knownBrands = collectKnownBrands(sourceKnowledge, toolResults);
        for (String brand : mentionedBrands) {
            if (knownBrands.stream().noneMatch(b -> b.contains(brand) || brand.contains(b))) {
                report.addIssue(Severity.MEDIUM, "品牌不在库中",
                    "回答提到「" + brand + "」但知识库和库存中不存在");
            }
        }

        // 3. 参数校验：提取数值型参数(续航/油耗/百公里加速等) → 对比知识库
        // ...

        return report;
    }
}
```

### 6.4 L3: 双模型交叉验证

**触发条件（不是每次都做，控制成本）**：
- 回答中包含具体价格数字
- 用户表达强购买意向("我要订"、"能签合同吗"、"今天就提车")
- L2校验发现异常但不确定
- 知识库检索置信度 < 0.4

```java
@Component
public class DualModelVerifier {

    private final ChatClient primaryClient;   // DeepSeek（主力）
    private final ChatClient reviewerClient;  // 另一个模型（或同模型低温度）

    /**
     * 双模型验证
     * @return 修正后的回答（如有问题），或原回答
     */
    public VerifiedResponse verify(String userQuery, String primaryAnswer,
                                    String knowledge, List<CarInventory> toolResults) {

        if (!needsVerification(primaryAnswer, knowledge)) {
            return new VerifiedResponse(primaryAnswer, false, List.of());
        }

        // Reviewer从审核员角度严格审查
        record ReviewVerdict(boolean hasIssues, List<String> issues,
                             String correctedAnswer, double confidence) {}

        ReviewVerdict verdict = reviewerClient.prompt()
            .system("""
                你是AI回答审核员。审查客服AI的回答是否与原始数据一致。

                审查标准：
                1. 价格必须与工具返回的精确数字一致（偏差>1%即为异常）
                2. 不能出现知识库中没有的品牌/车型/参数
                3. 不能编造卖点、优惠政策、库存状态

                如果发现问题，输出修正后的回答；没有则输出原回答。
                返回JSON: {"has_issues": bool, "issues": [...], "corrected_answer": "..."}
                """)
            .param("knowledge", knowledge)
            .param("tool_results", formatToolResults(toolResults))
            .param("primary_answer", primaryAnswer)
            .user(userQuery)
            .call()
            .entity(ReviewVerdict.class); // Spring AI结构化输出

        if (verdict.hasIssues()) {
            log.warn("双模型验证发现问题: {}", verdict.issues());
            return new VerifiedResponse(verdict.correctedAnswer(), true, verdict.issues());
        }
        return new VerifiedResponse(primaryAnswer, false, List.of());
    }

    private boolean needsVerification(String answer, String knowledge) {
        // 包含具体数字 → 触发
        if (answer.matches(".*\\d+(\\.\\d+)?\\s*万.*")) return true;
        // 购买信号 → 触发
        if (containsAny(answer, "订购", "下单", "合同", "定金", "提车")) return true;
        // 低置信度检索 → 触发
        // (从上下文传入)
        return false;
    }
}
```

## 9. 对话记忆与上下文管理

### 9.1 三层记忆架构

当前项目使用 `InMemoryChatMemory`（内存，重启丢失），需要升级为持久化三层记忆。

```
┌──────────────────────────────────────────────────────────┐
│  L1: 窗口记忆 (Working Memory)                            │
│                                                          │
│  存储: 最近N轮完整对话（N=20，约40条消息）                  │
│  用途: 每次LLM调用的直接上下文注入                          │
│  存储位置: Redis（快速读写）或 PostgreSQL                  │
│  淘汰策略: 超过N轮自动滚动窗口                              │
│  垃圾过滤: 闲聊轮次不计入窗口（只保留买车相关对话）          │
└──────────────────────┬───────────────────────────────────┘
                       │ 对话达到N/2轮时触发压缩
                       ▼
┌──────────────────────────────────────────────────────────┐
│  L2: 摘要记忆 (Summary Memory)                            │
│                                                          │
│  存储: LLM对历史对话的摘要（3-5句话）                       │
│  示例: "客户张先生在朝阳区，预算20-25万，想买新能源SUV，     │
│         关注比亚迪宋PLUS和特斯拉Model Y，                    │
│         对比后倾向宋PLUS因为空间更大，                       │
│         上轮问过落地价和试驾安排。"                          │
│  用途: 跨会话上下文恢复（客户隔天再来聊）                    │
│  存储位置: PostgreSQL                                     │
│  更新策略: 每N/2轮生成新摘要，覆盖旧摘要                     │
└──────────────────────┬───────────────────────────────────┘
                       │ 关键信息提取
                       ▼
┌──────────────────────────────────────────────────────────┐
│  L3: 核心事实 (Core Facts)                                │
│                                                          │
│  存储: 结构化用户画像                                      │
│  字段: 称呼、所在城市、预算范围、意向车型、购车用途、        │
│         偏好能源类型、到店意向、历史到店记录、              │
│         最近门店、联系方式                                 │
│  用途: System Prompt动态注入用户画像                       │
│  更新策略: 每次对话结束后LLM提取增量更新                    │
└──────────────────────────────────────────────────────────┘
```

### 9.2 垃圾信息过滤

不是所有对话都值得记忆：

| 过滤规则 | 操作 |
|---------|------|
| 纯闲聊消息 | 不计入窗口记忆，不触发摘要更新 |
| 注入攻击/恶意输入 | 计入安全日志，不计入记忆 |
| 重复消息（1分钟内相同内容） | 去重，只保留1条 |
| 超过24小时未活跃的会话 | 生成最终摘要存入L2，清理L1窗口 |
| 简短确认（"好的""嗯""OK"） | 保留但不触发摘要压缩 |

### 9.3 持久化实现

```java
@Component
public class PersistentChatMemory implements ChatMemory {

    private final JdbcTemplate jdbc; // 或 Redis

    // 存储消息
    public void add(String conversationId, List<Message> messages) {
        for (Message msg : messages) {
            jdbc.update(
                "INSERT INTO chat_messages (conversation_id, role, content, created_at) VALUES (?, ?, ?, ?)",
                conversationId, msg.getMessageType().name(), msg.getContent(), Instant.now()
            );
        }
        // 触发窗口裁剪
        trimWindow(conversationId, MAX_MESSAGES);
    }

    // 获取最近N条
    public List<Message> get(String conversationId, int lastN) {
        return jdbc.query(
            "SELECT role, content FROM chat_messages WHERE conversation_id = ? ORDER BY created_at DESC LIMIT ?",
            (rs, rowNum) -> new Message(
                MessageType.valueOf(rs.getString("role")),
                rs.getString("content")
            ),
            conversationId, lastN
        );
    }
}
```

### 10.1 从单Agent到多Agent路由

当前项目是单一 `CarSalesAgent`（LLM自主决策模式），随着场景复杂度提高需要引入意图路由：

### 10.2 动态温度策略

借鉴闲鱼智能客服的设计：

| 场景 | 温度 | 理由 |
|------|------|------|
| 信息查询（配置/参数/价格） | 0.1 - 0.3 | 要求事实准确，低创造性 |
| 售前推荐 | 0.4 - 0.6 | 需要一定的灵活表达，但不能编造 |
| 议价场景 | 0.7 - 0.9 | 需要灵活的谈判话术，共情和应对策略 |
| 情绪安抚 | 0.6 - 0.8 | 需要自然的共情表达 |
| 打招呼/闲聊 | 0.5 - 0.7 | 随意即可 |

```java
// 动态温度实现
public String chat(String userId, String message, IntentType intent) {
    double temperature = switch (intent) {
        case PRE_SALES  -> 0.3;
        case RECOMMEND  -> 0.5;
        case PRICE      -> 0.8;  // 议价需要灵活
        case EMOTIONAL  -> 0.7;
        case GREETING   -> 0.6;
        default         -> 0.3;
    };

    return ChatClient.builder(chatModel)
        .defaultOptions(chatOptions -> chatOptions.withTemperature(temperature))
        .build()
        .prompt()
        .user(message)
        .call()
        .content();
}
```

```java
    }
```

## 13. 技术选型决策记录

| 决策项 | 当前 | 短期(阶段1-3) | 中期(阶段4-5) | 长期(阶段6+) |
|--------|------|-------------|-------------|------------|
| **向量数据库** | Chroma (Docker) | Chroma | Chroma → Milvus (数据量>10万时) | Milvus |
| **Embedding** | BGE-M3 (硅基流动API) | 不变 | 评估本地Ollama部署 | 本地部署降低成本 |
| **业务数据库** | SQLite | SQLite | → PostgreSQL | PostgreSQL |
| **全文检索** | 无 | 内存倒排索引(小数据量) | Elasticsearch | Elasticsearch |
| **Reranker** | 无 | BGE-Reranker (硅基流动API) | 评估本地部署 | 本地部署 |
| **LLM** | DeepSeek | DeepSeek | DeepSeek + 备用模型 | 多模型路由 |
| **对话记忆** | 内存 InMemory | 内存 + 文件持久化 | PostgreSQL | PostgreSQL + Redis缓存 |
| **Agent模式** | 单Agent | 单Agent + Prompt路由 | 意图路由 + 子Agent | 完整多Agent |
| **消息队列** | 无 | 无 | 无 | RabbitMQ/Kafka (高并发时) |

### 关键技术取舍

1. **命题分块 vs 传统分块**：初期并行运行（新旧两个collection），A/B对比检索质量后再切换。

2. **Reranker的必要性**：BGE-M3混合检索已经比当前单路检索有质的提升。Reranker是锦上添花——召回topK=20已覆盖正确答案时，Reranker把它排到top3。先上线混合检索，如果topK命中率已经 > 90%，Reranker可降优先级。

3. **Milvus vs Chroma**：Chroma足够支撑当前规模(213块 → 预计扩充后 < 5000块)。切换到Milvus的触发点是：(a)向量量 > 10万 (b)需要多collection alias原生支持 (c)需要更高并发检索。

4. **多Agent的时机**：当前LLM自主决策模式在场景简单时是最高效的选择。引入多Agent的触发点：(a)售后/投诉场景上线 (b)不同场景需要差异化的温度和Prompt (c)需要独立的安全边界(售前不能误调到售后逻辑)。
