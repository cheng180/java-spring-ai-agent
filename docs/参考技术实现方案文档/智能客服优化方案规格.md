# 智能客服系统优化方案 — 完整实施规格

> **来源**：横纵分析调研 + grill 决策对齐  
> **状态**：ready-for-agent  
> **关联**：`参考技术实现方案文档/横纵分析调研文档.md`

---

## Problem Statement

当前智能客服系统（Spring AI 2.0 + Chroma + SQLite + DeepSeek）存在三个核心短板，导致客服不可用：

1. **知识库结构粗糙**：213块 TokenTextSplitter(500) 切分产物，语义单元不完整；每次启动全量刷新，无增量更新；单 collection 混杂车源/百科/话术三类数据，更新互相干扰
2. **模糊语义无法处理**：用户说「太贵了」「还有吗那款车」「感觉一般」时，系统没有指代消解能力，完全依赖LLM自由发挥。品牌匹配到多型号时不做热度排序，全量平铺
3. **无门店匹配能力**：6条门店硬编码，无法根据用户IP定位最近门店；热度维度缺乏门店粒度数据支撑

此外，RPA企微消息发送方案已弃用。

---

## Solution

分四个阶段实施，每个阶段独立可上线验证：

**阶段一：知识库框架重构**（基础设施）
- 三 Collection 拆分：`car-sku-facts` / `car-encyclopedia-facts` / `car-script-facts`
- 原子事实提取：车源用 SQL+模板渲染（不用 LLM），文档用 LLM 命题提取
- 每条事实带时序标记（ATEMPORAL/STATIC/DYNAMIC）、来源元数据、实体归一ID、内容哈希
- 各 Collection 独立蓝绿切换

**阶段二：IP定位 + 门店匹配 + 动态热度**（基础设施）
- GeoLocator 接口（先假数据，后期换 IP 定位服务）
- StoreLocator 接口（Haversine公式）
- HotCarRepository 接口（门店×车系热度，先假销量数据）
- 动态关键词表（启动时从 car_sku 去重构建，替代硬编码 CAR_KEYWORDS）

**阶段三：模糊语义路由**（核心业务逻辑）
- VagueQueryRouter 在 CarSalesAgent.chat() 中同步调用
- 三层匹配策略：精确SKU→直接答 / 品牌级→热度全列+追问 / 无匹配→级联兜底
- 级联兜底：历史车型确认 → 热度top3引导 → 纯追问（预算/用途/车型偏好）

**阶段四：混合检索**（检索质量提升）
- BM25 + BGE-M3 多路并行检索
- RRF 融合排序
- BGE-Reranker 二阶段精排

## User Stories

### 知识库框架

1. 作为系统运维人员，我希望车源价格变更时只更新 `car-sku-facts` collection，不影响百科和话术检索，避免因一次价格更新导致全局索引重建
2. 作为系统运维人员，我希望每个 collection 可以独立执行蓝绿切换，车源的频繁更新不会触发百科 collection 的版本切换
3. 作为开发人员，我希望车源数据（结构化）通过 SQL+模板渲染生成原子事实，不需要调用 LLM，以降低embedding刷新成本
4. 作为开发人员，我希望百科文档和销售话术通过 LLM 命题提取拆分为原子事实，每条事实自包含、可独立检索
5. 作为开发人员，我希望每条原子事实都打上时序标记（ATEMPORAL/STATIC/DYNAMIC），让检索时能区分「永久正确」和「可能过时」的信息
6. 作为开发人员，我希望每条原子事实带有实体归一ID，把「比亚迪宋PLUS」「宋PLUS」「BYD Song Plus」映射到同一实体
7. 作为开发人员，我希望增量更新时通过内容哈希检测变更，只重新处理变化的原子事实，而非全量重建

### IP定位 + 门店匹配 + 热度

8. 作为用户，当我说「你们在哪」时，我希望系统根据我的IP自动推荐最近的门店，而不是列出全国所有门店让我自己挑
9. 作为销售，当客服AI给用户推荐车时，我希望推荐顺序参考该门店的实际销量热度，热销款排前面
10. 作为开发人员，我希望 GeoLocator 接口先返回固定经纬度跑通链路，后续接入 IP 定位服务时只替换一个实现类
11. 作为开发人员，我希望启动时从 car_sku 表自动构建品牌/车系关键词表和别名映射，新增车系不需要改代码

### 模糊语义路由

12. 作为用户，当我说「太贵了」时，我希望系统能从对话历史中找到我刚才聊的车型，主动追问我的预算范围，并推荐同级别更便宜的替代车型
13. 作为用户，当我说「还有吗那款车」时，我希望系统能识别我指的是哪款车，确认后继续帮我看
14. 作为用户，当我说「比亚迪」时，我希望系统按热度列出比亚迪在售的全部车型，并引导我缩小范围（轿车还是SUV？预算多少？）
15. 作为用户，当我说「感觉一般」时，如果历史没有任何车型记录，我希望系统问我预算和用车需求来帮我推荐，而不是直接说「好的那您再看看」
16. 作为用户，当我给出精确车型（如「比亚迪宋PLUS DM-i 110km旗舰型」）且库存有货时，我希望系统直接报价介绍，不做多余追问
17. 作为销售，当用户表达模糊时，我希望AI先做一轮确认再进入检索流程，避免基于错误假设推荐完全不相关的车
18. 作为开发人员，我希望 VagueQueryRouter 的三层匹配（精确/品牌/模糊）各有明确的相似度阈值触发条件，代码层决策，不依赖LLM自主判断

### 混合检索

19. 作为用户，当我搜「省油的车」时，我希望 BM25 负责精确匹配「混动」「增程」「低油耗」等关键词，BGE-M3 负责语义理解「省油」和「低油耗」的等价关系
20. 作为开发人员，我希望混合检索的三路结果通过 RRF 融合后、再经过 BGE-Reranker 精排，确保最终送入 LLM 的 topK 文档是最相关的

## Implementation Decisions

### 决策1：知识库三 Collection 拆分

将当前单一 `car-sales-kb` collection 拆分为三个独立 collection。拆分维度是**更新频率和数据类型**，不是数据主题。

| Collection | 数据源 | 原子事实提取方式 | 更新策略 | 蓝绿切换 |
|-----------|--------|-----------------|---------|---------|
| car-sku-facts | car_sku 表 | SQL查询 + 模板渲染 | 事件驱动增量 | 独立 |
| car-encyclopedia-facts | 汽车百科知识库.md | LLM命题提取 | 文档级增量 | 独立 |
| car-script-facts | 购车引导话术.md + 情绪处理话术.md | LLM命题提取 | 文档级增量 | 独立 |

检索时并发查三个 collection，各自返回 topK，统一 RRF 融合 + Reranker。

### 决策2：原子事实提取双路径

**路径A（结构化数据）**：car_sku 行 → 模板渲染 → 自然语言文本。不使用 LLM。

```
模板："{model_name}，{color}，{energy_type}，指导价{guide_price}，
       全款销售价{sale_price}万，{spec_name}，{insurance}{vat}，
       车商：{owner_name}。{memo}"
```

每条事实带元数据：type=车源, sku_id, brand_name, series_name, energy_type, sale_price_wan, temporal_type=DYNAMIC (价格字段), source_hash

**路径B（非结构化文档）**：LLM结构化输出，返回 `List<AtomicFact>`。

```
AtomicFact {
  fact_id: string          // 来源文档ID + 序号，如 "encyc-byd-songplus-003"
  content: string          // 原子事实文本，一条可独立理解的陈述
  entity_id: string        // 归一化实体ID
  temporal_type: enum      // ATEMPORAL | STATIC | DYNAMIC
  source_doc: string       // 来源文件名
  source_hash: string      // 内容哈希
}
```

### 决策3：实体归一化

维护一张实体映射表，启动时从 car_sku 构建初始映射，手动补充同义词：

```
比亚迪宋PLUS → entity:car:byd:song-plus
BYD宋PLUS    → entity:car:byd:song-plus
宋plus       → entity:car:byd:song-plus
Song Plus    → entity:car:byd:song-plus
```

用于：知识库检索的 metadata 过滤；对话历史的车型指代消解；动态关键词表的构建。

### 决策4：时序标记

| 时序类型 | 定义 | 车源示例 | 百科示例 | 话术示例 |
|---------|------|---------|---------|---------|
| ATEMPORAL | 永远正确 | — | "水在100摄氏度沸腾" | "共情是销售的基本功" |
| STATIC | 在特定时间点变为真，此后不变 | brand_name, model_name | "宋PLUS于2024年发布" | — |
| DYNAMIC | 可能随时间变化 | sale_price, stock | "本月销量" | — |

### 决策5：蓝绿切换

每个 collection 维护两个物理 collection（如 `car-sku-facts-v1` 和 `car-sku-facts-v2`），应用层通过配置项指向活跃版本。

增量更新流程：
1. 检测变更（哈希对比 / DB事件）
2. 在备用 collection 上执行写入
3. 质量验证（数量校验 + 预定义召回测试）
4. 原子切换活跃版本配置
5. 旧版本保留作回滚快照

### 决策6：GeoLocator → StoreLocator → HotCarRepository 三层接口

```
GeoLocator.locate(userIp) → GeoLocation(lat, lng)
StoreLocator.findNearest(lat, lng) → StoreInfo(id, name, address, phone)
HotCarRepository.getHotCars(storeId, topN) → List<HotCar>
```

初期实现：
- GeoLocator 返回固定经纬度（杭州未来科技城）
- StoreLocator 用 Haversine 公式（上线即正确）
- HotCarRepository 读 store_car_hot 假数据表

接口分离确保后期替换实现类时零重构。

### 决策7：store_car_hot 表结构

```sql
CREATE TABLE store_car_hot (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    store_id      INTEGER NOT NULL REFERENCES store_config(id),
    series_name   TEXT NOT NULL,          -- 车系级热度（不是SKU级）
    sale_count    INTEGER DEFAULT 0,      -- 销量（真实DB对接后填充）
    inquiry_count INTEGER DEFAULT 0,      -- 咨询量
    stat_date     DATE NOT NULL,
    UNIQUE(store_id, series_name, stat_date)
);
```

粒度：门店 × 车系。假数据阶段手工插入几条记录覆盖主要车系。

### 决策8：动态关键词表

启动时从 car_sku 表执行：

```sql
SELECT DISTINCT brand_name, series_name FROM car_sku
WHERE sale_status = 1 AND is_deleted = 0
```

构建内存中的关键词映射：小写归一化文本 → 原始显示名 + 实体ID。新增车系不需改代码，重启即生效。

### 决策9：VagueQueryRouter 三层匹配策略

```
用户输入 → VagueQueryRouter.route(userId, message, conversationHistory)
    │
    ├── [L1] 精确匹配：brand_name + series_name 命中 + 相似度 ≥ 0.7
    │     → 返回 MatchResult(type=EXACT, carKey=..., needsConfirm=false)
    │     → 直接走正常检索+回复流程
    │
    ├── [L2] 品牌匹配：brand_name 命中但 series_name 不明确
    │     → 返回 MatchResult(type=BRAND, brand=..., hotModels=[...], needsConfirm=true)
    │     → 按热度降序列出全部型号 + 追问"您想看轿车还是SUV？预算大概多少？"
    │
    └── [L3] 模糊：无关键词命中，相似度 < 0.5
          → 返回 MatchResult(type=VAGUE, needsInference=true)
          → 进入级联兜底
```

### 决策10：级联兜底三步

```
[Step 1] 对话历史提取车型
    从最近10轮对话中，用动态关键词表匹配所有品牌/车系名
    命中 → 追问确认："您之前聊过XX，是在关心这款车吗？"
    未命中 → [Step 2]

[Step 2] 热度top3引导
    查 store_car_hot 取该门店销量top3车系
    命中 → "我们最近卖得最好的是A、B、C这三款，
           您是想了解其中哪款？还是我帮您按预算推荐？"
    未命中（冷门门店） → [Step 3]

[Step 3] 纯引导追问
    "您大概预算多少？主要通勤还是家用？喜欢轿车还是SUV？
     我帮您精准推荐～"
```

### 决策11：VagueQueryRouter 在 CarSalesAgent 中的位置

VagueQueryRouter 在 CarSalesAgent.chat() 里同步调用，位于 ChatClient 链之前：

```
chat(userId, message):
    1. 闲聊阈值检查（现有逻辑，不变）
    2. VagueQueryRouter.route(userId, message, chatMemory) → MatchResult
    3. if needsConfirm → 直接返回追问文本，不进入 ChatClient 链
    4. if needsInference → 注入提取的上下文到 system prompt
    5. 正常调用 chatClient.prompt()...
```

### 决策12：RPA 已弃用

企业微信 RPA 消息发送方案不再实施。第九章全部跳过。

### 决策13：未覆盖项（后续阶段）

以下内容不在本次实施范围内，但在整体路线图中预留：

- **多问题拆分**：用户一口气问多个问题时的拆分+并行检索+合并回答
- **增量更新触发机制**：首版用启动时全量刷新 + 手动触发接口，事件驱动（DB变更监听/文件WatchService）放在下一版
- **幻觉防御三层体系**：当前仅保留 L1（提示词规则），L2（规则校验引擎）和 L3（双模型验证）在模糊路由上线后评估必要性
- **对话记忆持久化**：InMemoryChatMemory 替换为 PostgreSQL 三层记忆（窗口→摘要→核心事实），在知识库稳定后实施
- **多Agent路由**：意图路由 + 子Agent拆分（售前/售后/投诉/情绪安抚），在单Agent + VagueQueryRouter 验证有效后实施

## Testing Decisions

### 测试原则

- 只测试外部可观察行为，不测试内部实现细节
- 每个模块有独立的单元测试，Mock 外部依赖（VectorStore、JdbcTemplate、LLM调用）
- 端到端测试覆盖完整对话链

### 测试模块与策略

| 模块 | 测试方法 | 关键场景 |
|------|---------|---------|
| AtomicFactExtractor（SQL路径） | 单元测试 | 验证模板渲染输出格式正确；验证时序标记赋值 |
| AtomicFactExtractor（LLM路径） | 单元测试 + Mock LLM | 验证命题拆分数量合理；验证每条事实自包含 |
| VagueQueryRouter | 单元测试 | 精确匹配→L1；品牌匹配→L2；无匹配→L3；历史命中→Step1 |
| StoreLocator | 单元测试 | 固定经纬度→最近门店正确；多个等距门店→任选一个 |
| HybridRetriever | 集成测试 | 三路并发检索→RRF融合→结果数 ≤ topK×3 |
| 知识库增量更新 | 集成测试 | 改一条车源→只重建该条→collection总量不变 |
| 对话链路 | 端到端测试 | "你好"→打招呼；"比亚迪"→全列+追问；"太贵了"→历史+引导 |

### 参照现有测试模式

项目当前无测试代码。采用 Spring Boot Test + JUnit 5 + Mockito 标准栈。知识库相关测试使用 TestContainers 或内嵌 Chroma。

## Further Notes

### 与横纵分析调研的关联

横纵分析报告指出：卖好车在2020年后面临融资断档和下游经销商萎缩的双重压力，新能源下沉和汽车出海是两条可能的增长曲线。智能客服系统直接服务于「新能源下沉」战略——帮助经销商以更低的人力成本覆盖更多线上咨询。因此，模糊语义处理和知识库质量是系统成败的关键，直接决定了客服是否「可用」。

### 与现有设计文档的关系

本次优化调整了原有7阶段路线图的优先级：
- 原阶段1（检索质量提升） → 现调整为阶段四
- 原阶段3（模糊语义+多问题） → 现调整为阶段三（仅模糊语义，多问题拆分后移）
- 原阶段5（动态配置+多门店） → 前移到阶段二
- 原阶段2（幻觉防御） → 后移，仅保留L1
- 原阶段4（知识库动态更新） → 融入阶段一
- 原阶段6（企微RPA） → 已弃用
