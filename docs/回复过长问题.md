# 回复过长问题

## 背景

智能客服 Agent 对接微信（macan 企微客服）后，LLM 生成的回复内容过长，不适合移动端微信聊天场景。微信单条消息舒适阅读长度约 150-200 字（3-5 行），当前回复在命中车系时经常远超此范围。

## 根因分析

问题出在检索层，而非 LLM 生成层。

### 当前检索链路

```
用户消息
  │
  ├─ EntityResolver 别名匹配 → entitySeries
  │
  ├─ 阶段一：父块 HybridRetriever (BM25 + BGE-M3 → RRF)
  │     type=车源, level=parent, topK=3, threshold=0.6
  │     → hitSeries
  │
  └─ 命中车系？
       ├─ 否 → 子块泛检索 topK=5 + 百科/话术 topK=3
       │
       └─ 是 → 阶段二：每个车系子块全量展开 topK=20（无条件）
                ↓
              全部注入 system prompt → LLM 看到大量 SKU → 自然输出长篇
```

关键代码：`CarSalesAgent.retrieveContext()` 第 290 行注释——"决策：全量，不截断"。命中车系后，每个 series 的子块以 topK=20 展开，全部注入 system prompt。System prompt 虽然写了"回复简洁精准"，但上下文里塞 20 个 SKU 是在给 LLM 发相反的信号。

### 为什么不能简单减少上下文

减少 RAG 上下文会增加幻觉风险（编造价格、配置、库存数）。当前全量注入子块是防止 SKU 细节幻觉的直接手段。

## 可能的解决方案

### 方案 A：分层检索 —— 默认轻量，追问展开

**思路**：`retrieveContext()` 默认只注入父块（车系摘要：有无库存、价格区间），用户追问细节时才展开子块。

```
第一轮："有比亚迪宋吗？"
  → 只检索父块 → "有的，宋PLUS 12-16万，宋Pro 10-14万，想看哪款？"
  → LLM 只看到父块，自然简短

第二轮："宋PLUS有什么配置？"
  → 命中追问判断 → 展开子块 → 返回具体 SKU 详情
```

**追问判断逻辑位置**：放在 `retrieveContext()` 内部，不改 VagueQueryRouter。路由层负责"问题类型"，检索层负责"根据类型拿多少数据"。

**追问判断方式**（待定）：
- 规则检测：当前消息含"配置""版本""参数""详细""具体""多少钱""区别"等关键词 → 展开
- 历史检测：最近一轮对话是否在同车系上下文内
- LLM 工具调用：不新增工具，收敛到现有 `searchInventory`——LLM 需要细节时自己调

**优点**：根因解决，输入少则输出短，幻觉由 Tool Calling 兜底
**缺点**：改动涉及检索核心逻辑，需要验证各场景下追问判断的准确率

### 方案 B：Prompt 约束 + 后处理截断

**思路**：不改检索，在 prompt 层加强长度约束，代码层做兜底截断。

- System prompt 增加："每次回复不超过 3 句话，总字数控制在 150 以内"
- `MacanChatController.chatForMacan()` 或 `CarSalesAgent.chat()` 返回前，在第一个完整句子后截断兜底

**优点**：改动最小，低风险，可快速上线
**缺点**：LLM 不会精确数中文字数；硬截断可能截掉关键信息（地址、电话）；不解决根本问题（上下文仍然过长，token 浪费）

### 方案 C：子块摘要化

**思路**：不改检索量，但在注入上下文前对子块做摘要压缩。

- 子块不再注入完整文本，改为结构化摘要：`车型 | 价格 | 续航 | 库存`
- 例如 20 个 SKU 压缩为一张简表，而非 20 段全文

**优点**：信息密度高，不丢数据，LLM 更容易产出简洁回复
**缺点**：摘要格式需要约定；某些配置细节（如"带座椅加热的真皮座椅"）在摘要中丢失，追问时仍需展开

### 方案 D：硬限制字符数

**思路**：在 prompt 中写"回复不超过 20 字"或类似硬约束。

**不推荐**。LLM 不会数中文字数，硬限制越小偏差越大。且 20 字无法装下合格客服回复——门店地址电话、多车型推荐等场景最少需要 20-30 字，硬压会损害服务质量。

## 方案对比

| 维度 | A 分层检索 | B Prompt+截断 | C 子块摘要 | D 硬限字数 |
|------|-----------|--------------|-----------|-----------|
| 根因解决 | ✅ 是 | ❌ 治标 | ⚠️ 部分 | ❌ 否 |
| 幻觉风险 | ⚠️ 依赖 Tool Calling 兜底 | ✅ 不改检索 | ✅ 不改检索 | ✅ 不改检索 |
| 改动量 | 中 | 小 | 中 | 小 |
| 用户体验 | 最好 | 可能截断关键信息 | 好 | 差 |
| 可快速上线 | 否 | 是 | 否 | 是 |
