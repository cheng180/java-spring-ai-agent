# 回复过长问题 — 解决评估文档

- **评估日期**：2026-08-03
- **评估对象**：Issue #21（分层检索/渐进式披露）及其拆分工单 #22–#27
- **关联文档**：《回复过长问题》（`docs/回复过长问题.md`，问题与根因记录）、《Spring AI智能客服设计方案》
- **结论先行**：方案 trade-off 划算，**不会引入比现状更大的问题**——所有失效模式都朝"退回现状"方向降级，正确性/幻觉敏感路径零退化。存在 4 项需跟踪的尾部风险，均附低成本加固建议（见第五、六节）。

---

## 一、问题与根因回顾

微信端（macan 企微客服接入）单条消息舒适阅读长度约 150–200 字，当前命中车系的回复经常远超此范围。

**根因在检索层，不在生成层**：用户消息命中车系后，检索把每个车系的多条车源 SKU 全文（每车系 topK=20，无条件不截断）一次性注入 system prompt。上下文塞满 SKU 等于给 LLM 发"列清单"的信号，系统提示词里的"简洁精准"被反向覆盖。

**约束**：不能简单削减上下文。全量注入子块正是防 SKU 细节幻觉（编造价格/配置/库存）的直接手段，减上下文 = 加幻觉风险。方案的难点在于"缩短回复"与"幻觉红线"两个目标互斥。

## 二、采纳方案：分层检索（渐进式披露）

按用户查询粒度分四级，注入不同详细程度的上下文，让 LLM 每轮只拿到"这一轮该给的信息"，后置反问引导进入下一层：

| 级别 | 触发形态（示例） | 注入内容 | 预期回复形态 |
|---|---|---|---|
| BRAND 品牌级 | "有比亚迪吗" | 不查向量库；在售车系数量 + 热度 top1 车系名 + 级别指令 | 确认库存、推荐一款、反问偏好 |
| FAMILY 车系族级 | "比亚迪秦"（命中多个同品牌车系） | 命中车系的父块（截断到"在售款型"段之前） | 只讲命中车系，问想深入哪个 |
| SERIES 车系级 | "海豹"（单一车系） | 该车系完整父块（含在售款型） | 只讲该车系，末尾问是否深入 |
| UNRESTRICTED 未受限 | 细节词（多少钱/配置/对比…）、跨品牌对比、无法归类 | **与现状字节级一致**（全量子块展开/泛检索） | 维持现状，防幻觉手段不动 |

配套机制：

- **粒度分类器**：纯逻辑、零基础设施依赖，表驱动测试锁定；判定序"细节触发词 → 实体命中 → 品牌关键词 → 兜底未受限"
- **fail-safe 三保险**：截断锚点失效 → 保留全文（宁长勿错）；父块取不到 → 降级未受限（绝不注入空上下文）；无法归类 → 未受限
- **工具抑制**：受限级别上下文附"本轮不调库存查询/全量列表工具"指令（软约束，不加硬 LIMIT——见风险 R1）
- **大模型始终在环**：不做代码模板直接回复（吸取模板路由劫持正常查询被整体回退的历史教训）
- **幻觉红线数据修正**：关键词表/实体映射补"仅在售"过滤，防止品牌摘要宣称下架车系"有库存"

## 三、Trade-off 总体评估

**核心结论：这是一次不对称的赌注。**

方案用"部分查询多一轮对话 + 长回复的尾部残留风险"换取"移动端主流场景长回复的根因治愈 + 细节场景零退化"。其安全性来自一个关键设计属性——**所有失效模式都朝"退回现状"方向降级，而不是朝"比现状更糟"方向**：

| 失效场景 | 设计行为 | 最坏后果 |
|---|---|---|
| 分类失败 / 无法归类 | → UNRESTRICTED | 回复偏长（现状），无正确性回归 |
| 截断锚点失效 | → fail-safe 保留全文 | 宁长勿错 |
| 父块取不到（下架车系实体残留等） | → 降级未受限 | 绝不注入空上下文 |
| 细节 / 对比查询 | → 全量注入不动 | 幻觉红线场景零降级 |
| LLM 违反工具抑制指令 | → 全量 SKU 回流 | 长回复间歇复发（见 R1） |

幻觉风险最高的场景（报价、配置、参数、跨车型对比）恰恰保留全量注入——**正确性敏感路径零退化**是这套方案最重要的安全属性。叠加 #23 黄金锚点（UNRESTRICTED 路径字节级锁死）与提交级回滚粒度，最坏情况是"没治好转长回复"，而不是引入新的正确性/幻觉问题。

## 四、识别出的风险与代价（按重要性排序）

### R1. 工具抑制是软约束，且代码里存在已核实的"决堤口"⚠️

受限级别"本轮不调库存工具"仅靠级别指令 + 提示词实现（规格明确将硬 LIMIT 列为 Out of Scope）。经核实 `CarSalesTools.searchInventory()`（第 62–77 行）：**`matched` 非空分支的 SQL 没有 LIMIT**（仅空分支有 `LIMIT 15`）。一旦 LLM 违反指令在品牌级轮次调用 `searchInventory("比亚迪")`，全量 SKU 回流上下文，长回复**间歇性复发**——"时好时坏"的症状比一致的长回复更难排查。这是方案里有意识的赌注，赌的是 LLM 指令服从率。

> ✅ **后续已修复**（2026-08，`b9c59c2` fix(#38)）：`searchInventory` matched 分支已补 `LIMIT 30`（`SEARCH_MATCHED_LIMIT`），决堤口封堵；`getAllCars` 摘要上限 15（`ALL_CARS_LIMIT`）。

### R2. 分类器黑盒运行，现有日志无法定位误分类 ⚠️

对话日志（`CarSalesAgent.logConversation`）目前只记录命中实体，**不记录分类级别**。上线后若出现"该给细节却只给了摘要"的反馈，无法从日志反查当时判成了哪一级、因何触发。User story #15 设想"用现有日志观察回复长度"，但长度可观察、归因不可观察。

### R3. 触发词表是封闭集，意图漏判导致体验降级（可自愈）

细节触发词表为固定 15 个词。筛选/最高级意图——"最便宜的SUV""七座的""适合家用的"——不在词表内，会被归入受限级别，LLM 在薄上下文 + 工具抑制下只能用摘要打太极。用户被反问后重问即自愈，不是正确性问题，但微信端每多一轮对话都是流失点。反方向（简单查询误判为 UNRESTRICTED）只是维持现状，无害。

### R4. 对 EntityResolver 的依赖被放大，而 #9 尚未解决

Issue #9（`needs-triage`）已证实别名覆盖率仅 33%（22/66 条目有别名），此前靠 embedding 父块检索兜底。新方案中 BRAND/FAMILY/SERIES 分支**只信 EntityResolver + 关键词表**，embedding 兜底仅在完全 miss（→ UNRESTRICTED）时生效。**部分命中无兜底**：如"比亚迪秦"只解析出秦PLUS、漏掉秦L，FAMILY 会静默降级为 SERIES，回答范围窄于用户意图（可通过重问自愈）。本方案落地后，分级质量与 EntityResolver 质量绑定，#9 优先级应实质性上调。

### 边界说明（不算新问题，但需明确生效范围）

- **语义 miss 查询不在修复覆盖内**："byd多少钱""混动车多少钱"等走 UNRESTRICTED，长回复依旧。方案只覆盖实体/关键词可解析的查询——这是生效边界，不是回归。
- **历史回放稀释**：ChatMemory 40 条窗口 / macan Redis 历史保存上一轮 assistant 的长回复（含全量 SKU），后续薄上下文轮次 LLM 仍可能从记忆复述。影响有限但存在。
- **"实体数 == 品牌全部在售车系数"启发式**：依赖 entity_mapping 与 car_sku 两个数据源的在售集合一致。#22 已统一补在售过滤，风险降低，但双数据源结构本身仍在。

## 五、结论

**该 trade-off 不会带来更大的问题。** 输的上限是"回复偶尔还是长 + 部分查询多一轮对话"，赢的是移动端主流场景的根因治愈与细节场景零退化。fail-safe 方向设计（宁长勿错、降级回现状、黄金锚点、提交级回滚）表明规格已吸取模板路由劫持查询被整体回退的历史教训。**建议按 #23 → #24 → #25/#26 → #27 顺序推进。**

## 六、加固建议（低成本，随 #24–#27 顺手落地）

1. **对话日志注入分类级别**（对应 R2）：在 `logConversation` 中追加判定的级别与触发依据（命中实体/关键词/触发词），几行代码，是上线后可排查性的前提。
2. **`searchInventory` matched 分支补 LIMIT**（对应 R1）：规格虽列为 Out of Scope，建议至少加保守上限（如 30 行）。现在改一行，比上线后追查间歇性长回复便宜得多。
3. **#9 提优先级**（对应 R4）：作为本方案的关联项跟踪；别名覆盖率从此直接决定分级质量。
4. **上线观察指标**（对应 R1/R3）：按冒烟清单核对 8 类查询回复长度落回 150–200 字之外，持续观察"受限级别轮次的工具调用率"——该指标是软约束是否失守的直接信号。
