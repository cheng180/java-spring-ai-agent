## 1. 背景与动机

### 1.1 现状

当前「小张」顾问的目标体系是隐式的：

- system prompt 以**卖车**为主线（乔哈里窗口四动作、渐进式披露）；
- 「到店」是聊出来的副产品——场景规则 3b 要求推荐后"自然邀请到店"，场景 4（试驾/到店意向）会"建议留联系方式方便门店对接"；
- **没有任何机制承接联系方式**：客户在对话里给出了城市和电话，信息只存在于会话记忆里（macan 路径甚至是每请求一次性会话），对话结束即丢失；
- 没有"销售"这个角色的概念——AI 永远按全能销售顾问的姿态服务。

### 1.2 业务约束（本次设计的第一输入）

> **身份一（首要身份）**：客服的终极目标**不是引导到店**，而是**首先获取用户的位置和电话号码**。获取之后，销售可以加客户微信并跟进（加微信操作本身不在本项目范围内）。
>
> **身份二（条件身份）**：**替代销售**——当销售不空闲时，替代销售做引导到店服务。

### 1.3 目标优先级（由此确立）

| 优先级 | 目标 | 说明 |
|---|---|---|
| **P0** | 收集位置 + 电话号码 | 贯穿整段对话的第一目标；拿到即落库、交接 |
| **P1** | 替代销售做到店引导 | 线索收集后（或客户拒给时），对话仍在继续且无人工接管 → 顶上销售的角色 |
| **P2** | 准确回答车辆咨询 | 现有渐进式披露 / 防幻觉 / 分级检索规则全部保留，作为服务底座 |

**「引导到店」从终极目标降级为 P1**——它仍然发生，但只作为"销售不空闲时的替代服务"，不再驱动对话节奏；对话节奏改由线索收集驱动。

## 2. 身份激活机制：AI 首接，接管即退

### 2.1 "销售不空闲"的定义

AI 项目无法实时感知销售本人的忙闲，采用**架构性定义**（已确认）：

- AI 永远是第一接待人（现有架构使然：macan 侧无人工接管时消息就打到 AI）；
- **销售没有接管对话 = 销售不空闲**。AI 在场服务本身就是"替代"；
- 销售一旦接管（macan 侧现有转人工机制），AI 自然退出——**此机制已存在，本次不改**。

因此两个身份不是并行开关，而是**同一通 AI 对话内的阶段演进**：

```
客户进线（无人工接管 ⇒ 销售视为不空闲）
  │
  ▼
┌─────────────────────────────────────────────────┐
│ 阶段A【身份一·线索收集】                          │
│  正常答车（P2 规则不变）+ 寻找自然时机收集城市/电话 │
│  拿到一项落库一项（saveLead，幂等）                │
└──────────────┬──────────────────────────────────┘
               │ 城市+电话齐备 → saveLead → 交接话术
               │（"稍后会有同事联系您跟进"）
               ▼
┌─────────────────────────────────────────────────┐
│ 阶段B【交接】                                    │
│  线索状态 CAPTURED，销售看到线索后加微信/跟进      │
│  （加微信、跟进流程均在本项目范围外）              │
└──────────────┬──────────────────────────────────┘
               │ 对话仍在继续 且 销售尚未接管
               ▼
┌─────────────────────────────────────────────────┐
│ 阶段C【身份二·替代销售到店引导】                   │
│  介绍门店、邀请试驾、提议预约时间、确认到店安排      │
│  （复用 getStoreInfo 等现有能力）                 │
└─────────────────────────────────────────────────┘

  任意阶段：销售（人工）接管 → AI 退出（现有机制，不变）
```

### 2.2 例外路径

- **客户拒给电话**：不强求，`refuse_phone` 置位，跳过阶段B 直接进入正常服务（仍可应客户要求做到店引导）；后续只保留弱时机，不再主动索要。
- **客户带着明确到店/试驾意图进线**（现场景4）：到店意图本身就是收集时机——问城市（getStoreInfo 本就需要）→ 给门店信息 → 顺势要电话"方便门店同事对接"。P0 优先于"赶紧把地址报完"。

## 3. 对话策略

### 3.1 收集顺序与时机

**先位置（城市），后电话。** 城市是低敏感信息且 getStoreInfo 天然需要；电话是高敏感信息，放在已提供价值之后索要。

| 时机 | 话术形态（示例，非冻结） |
|---|---|
| 客户问门店/地址/试驾 | "您在哪个城市？我帮您查最近的店" → 报完门店后："方便留个电话吗？门店同事好跟您对接试驾" |
| 推荐 2~3 款车型收尾 | "您看车主要在哪个城市？我帮您留意着最近的店，有合适的方便通知您" |
| 客户表达明确购车意向 | 收尾时："留个联系方式吧，有优惠或者现车消息我让同事第一时间告诉您" |

**收集纪律（进 prompt 的硬规则）：**

1. 一轮最多推进一项（先城市或电话其一），不连环追问、不审问式索要；
2. 必须嵌在服务流程里顺势提出（查店前、约试驾前、推荐收尾时），不凭空突兀索要；
3. 客户拒绝 → 立即停止索要，致歉一句带回正常服务；同一会话内不再主动提起；
4. 已有完整线索后**绝不重复索要**（由代码注入的线索状态兜底，不依赖 LLM 记忆）。

### 3.2 交接话术（线索齐备后）

统一语义："好的～稍后会有同事联系您跟进，您有任何问题也随时找我。"

- **不承诺具体联系时间**（"马上""十分钟内"等一律禁止）；
- **不说"我加您微信"**——加微信不在 AI 能力范围（项目范围外），只说"会有同事联系您"；
- 交接后对话不终止：客户继续聊车，按 P2 正常答；客户聊到店，进阶段C。

### 3.3 阶段C：替代销售的到店引导

线索齐备（或客户拒给）后，若对话继续且无人工接管，AI 顶替销售角色：

- 主动邀请试驾、提议预约时间（"这周末方便的话我帮您约个试驾？"）；
- 复用 `getStoreInfo(city)` 提供地址/电话/营业时间；
- 遵守现有幻觉红线：不编造门店信息、不承诺没有的现车；
- 到店引导**不以线索完整为前提**——客户拒给电话但想到店，照常服务。

## 4. 系统改造设计

### 4.1 数据模型：`customer_lead` 表（AI 侧，已确认）

```sql
CREATE TABLE IF NOT EXISTS customer_lead (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    user_key      TEXT NOT NULL,             -- web=userId；macan=externalUserId
    source        TEXT NOT NULL,             -- 'web' | 'macan'
    city          TEXT,                      -- 位置：城市级（对齐 getStoreInfo 粒度）
    phone         TEXT,                      -- 11 位大陆手机号
    intent_series TEXT,                      -- 意向车系（EntityResolver 命中时顺带写，辅助销售跟进）
    status        TEXT NOT NULL DEFAULT 'PARTIAL',  -- PARTIAL | CAPTURED | REFUSED
    refuse_phone  INTEGER NOT NULL DEFAULT 0,      -- 1=客户明确拒给电话
    handed_over   INTEGER NOT NULL DEFAULT 0,      -- 1=已输出过交接话术
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    UNIQUE(user_key, source)                 -- 幂等：同一客户 upsert，不重复建行
);
```

- **位置粒度 = 城市**，与现有门店定位能力（`getStoreInfo(city)`）对齐；街道级定位不在本期。
- `intent_series` 首版即接：`CarSalesAgent` 每轮已有 `matchedSeries`，saveLead 落库时顺带写入，成本极低、对销售跟进价值高。

### 4.2 新增工具：`saveLead(city, phone)`

LLM 拿到位置/电话时的**唯一落库入口**（加入 `CarSalesTools`，prompt 工具箱同步登记）：

- 两项参数均可选，至少传一项；电话做格式校验（`^1\d{10}$`）；
- 按当前会话的 user_key 幂等 upsert；已有值不被空值覆盖；
- 返回状态文本驱动 LLM 下一步：
  - `"已记录城市（北京）。还差电话号码，线索才算完整。"`
  - `"线索已完整（城市：北京，电话已记录）。请输出交接话术，之后不要再索要联系方式。"`
  - `"电话号码格式不对（需 11 位手机号），请与客户确认。"`

不新增 `getLeadStatus` 工具——线索状态由代码注入（§4.3），少一次工具往返，且确定性更高。

### 4.3 线索状态注入（确定性，不依赖 LLM 记忆）

`CarSalesAgent.chat()/chatStream()` 入口，按 user_key 查 `customer_lead`，向本轮 system 上下文追加 `## 线索状态` 段：

| 库内状态 | 注入文本（要义） |
|---|---|
| 无记录 | `城市和电话均未收集。本轮先正常服务，寻找自然时机收集（先城市后电话）。` |
| PARTIAL | `已收集城市（北京），电话未收集。寻找自然时机收集电话。` |
| CAPTURED | `线索已完整（城市：北京，电话 138****0000）。不要再索要联系方式；对话继续时按替代销售身份做到店引导。` |
| refuse_phone=1 | `客户已拒绝提供电话，不要再索要。正常服务即可。` |

要点：

- **电话脱敏注入**（`138****0000`），防止 LLM 在回复里复述完整号码；
- **macan 路径的关键改造**：当前 `conversationId` 是每请求一次性的（`externalUserId-UUID`），`userId` 仅用于日志。线索状态要跨请求生效，必须用**稳定的 externalUserId 作为 user_key**——请求协议不变（`userId` 字段本就存在），只是 AI 项目从"仅记日志"升级为"同时作为线索键"。若 macan 未传 userId：降级为按一次性会话处理（saveLead 仍可落库，user_key 记为 `anon-<conversationId>`，靠电话号码事后查询），注入不生效。
- 组装位置建议并入 `RetrievalContextAssembler` 之外的独立 `LeadContextInjector`（线索是业务状态，不是检索结果，不混入 RAG 上下文）。

### 4.4 PromptTemplates 改造

**新增**「身份与目标层级」块，置于人设之后、乔哈里窗口之前（全文最高优先级语义），冻结措辞草案见**附录 A**。

**调整**现有场景规则：

- 场景 3b 末尾"自然邀请到店" → 改为"自然收集城市（为推荐收尾服务），不做到店邀请"（到店邀请移到身份二）；
- 场景 4（试驾/到店意向）→ "问清城市 → getStoreInfo(city) → **索要电话（P0）** → 线索齐备后按线索状态指令走交接或到店引导"；
- 工具箱清单补登 `saveLead`（顺带修正已知的 getHotCars 未登记问题，见链路梳理 §7.3）。

### 4.5 响应侧信道：lead 字段回传 macan

销售要能"看到"线索。首期不做推送，做法：

```json
{ "reply": "AI 生成的回复文本",
  "lead": { "city": "北京", "phone": "13800000000", "status": "CAPTURED", "new": true } }
```

- `reply` 语义完全不变，macan 不消费 `lead` 也不受影响（向后兼容）；
- `lead` 由 `MacanChatController` 在 agent 返回后按 externalUserId 查一次库组装（每请求一次 SELECT，成本可忽略）；`new=true` 表示本轮有新增/变更，便于 macan 侧去重展示；
- Web 入口（`ChatController`）首期不加此字段，线索直接查库；
- **销售消费方式的远期选项**（本期不做）：管理后台线索列表 / 企微通知推送 / 回写公司 CRM 接口。

### 4.6 接口签名影响

`ChatService.chatWithHistory(conversationId, userMessage, history)` 目前把稳定 userId 混在一次性 conversationId 里。建议扩为：

```java
String chatWithHistory(String conversationId, String stableUserId, String userMessage, List<Message> history);
```

stableUserId 用于线索查询/落库与状态注入；conversationId 仍负责一次性记忆隔离。仅一个实现、一个调用方，改动面可控。

## 5. 边界与非目标

1. **加微信操作不在本项目范围**。AI 只说"会有同事联系您"；加微信由销售人工 / macan 侧完成。prompt 明令禁止 AI 声称自己加微信。
2. **销售跟进流程不在本项目范围**。AI 项目交付物是：`customer_lead` 表 + 响应 `lead` 字段。
3. **销售实时通知不做**（首期）。销售侧轮询/查看线索即可；推送是远期扩展。
4. **不改现有架构底座**：闲聊门、VagueQueryRouter、分级检索、两阶段召回、防幻觉红线全部原样保留——本设计是在现有链路上叠加目标层，不是重构。
5. **街道级定位不做**。位置粒度=城市，与 getStoreInfo 对齐。

## 6. 合规与隐私

- 电话号码属个人信息：**只接受客户主动给出**，不诱导、不胁迫、拒绝即止；
- 索要话术说明用途（"方便门店同事跟您对接"），给客户拒绝的空间；
- **完整电话不进对话日志**：`logConversation` 中 reply/msg 若含电话需脱敏（或线索信息只走结构化字段，不混入 msg 文本）；线索状态注入同样脱敏；
- 数据留存与删除策略（个人信息保护要求）列入开放问题，上线前需定。

## 7. 验收标准

| # | 场景 | 预期 |
|---|---|---|
| 1 | 客户问"你们店在哪" | 先问城市 → 报最近门店 → 顺势索要电话 |
| 2 | 客户给出电话（格式正确） | 触发 saveLead，`customer_lead` 落库，status=CAPTURED（若城市已有） |
| 3 | 线索齐备后的下一轮 | 注入"线索已完整"，AI 输出交接话术且**不再索要**联系方式 |
| 4 | 交接后对话继续、无人工接管 | AI 以替代销售身份做到店引导（邀请试驾/预约） |
| 5 | 客户拒给电话 | 不再追问，refuse_phone=1，正常服务继续 |
| 6 | 客户报错误电话（10位/含字母） | saveLead 校验失败，AI 请客户确认，不落库 |
| 7 | macan 连续两次请求（同一 externalUserId） | 第二次请求的回复体现第一次已收集的线索状态（不重复索要） |
| 8 | macan 响应 | `reply` 语义不变；线索变更时附 `lead` 字段 |
| 9 | 任何情况下 | AI 不说"我加您微信"，不承诺具体联系时间 |
| 10 | 纯闲聊/拒给线索的客户 | 现有闲聊门、分级检索行为不变 |

## 8. 开放问题

1. **线索留存期与删除流程**（个人信息合规）——上线前必须定；
2. **销售侧消费形态**：查库 / 管理后台 / 企微推送？需与 macan 团队对齐；
3. **与公司 CRM 的关系**：若同一电话已在 CRM 存在，去重与归属规则（远期对接时定）；
4. **macan 是否保证 externalUserId 必传**：若否，匿名线索（anon- 前缀）的销售可用性会打折扣，需推动 macan 侧保证。

## 附录 A：System Prompt 新增块（冻结措辞草案）

置于人设之后、"核心方法：信息差管理"之前：

```text
=== 身份与目标层级（最高优先级） ===
你有两层身份，按优先级行事：
1.【首要身份·线索收集】你的终极目标不是引导到店，而是在服务过程中自然获取客户的
  所在城市和电话号码。两项齐备后立即调 saveLead 落库，然后告诉客户"稍后会有同事
  联系您跟进"，此后不再索要联系方式。
2.【次级身份·替代销售】线索齐备（或客户明确拒给）后，若对话仍在继续且没有人工同事
  接管，你替代销售提供到店引导服务：介绍门店、邀请试驾、提议预约。

目标优先级：收集位置和电话 > 替代销售做到店引导 > 回答车辆问题。

收集纪律：
- 先城市后电话；一轮最多推进一项，不连环追问；
- 嵌在服务里顺势提（查店前、约试驾前、推荐收尾时），不凭空索要；
- 客户拒绝即止，致歉后带回正常服务，不再主动提；
```
