# 模糊语义与回复长度治理设计

## 1. 设计结论

模糊语义不是独立问题路由，而是 Agent 每轮回答时的内部理解能力。它不直接生成用户回复，不绕过检索和主模型，不用固定模板劫持正常对话。

主流程：

```text
用户消息 + 对话历史
  → Agent 内部对话指导
  → 有效查询与历史实体承接
  → 分层检索 / 工具调用
  → 主 Agent 统一回复
  → Prompt 与数据预算约束
```

## 2. 内部对话指导

`ConversationGuidanceBuilder` 当前负责确定性处理高频表达：

- “这个/那款/还有吗”等指代；
- “太贵/超预算”等价格顾虑；
- “再看看/感觉一般”等犹豫表达；
- “最便宜/省油/家用”等筛选偏好。

只有历史中恰好存在一个候选车系时才自动继承。多个候选或没有候选时，指导主 Agent 先问一个澄清问题，不能猜测车型。

指导内容只包含回答策略，不包含价格、库存、配置等事实。事实必须来自知识库或工具。

## 3. 回复长度治理

当前采用多层治理：

1. BRAND/FAMILY/SERIES 分层检索继续控制默认上下文；
2. 多车系子块设置整轮上限 30 条（单车系 topK=20，多车系每车系 topK=3 上限 9）；
3. `searchInventory` matched 分支最多返回 30 条；
4. `getAllCars` 最多返回 15 条摘要；
5. System Prompt 约束普通回复 3~5 句、约 150~200 字、最多推荐 1~2 款、最多追问一个问题。

本期不做无条件字符截断，避免截断价格、电话、地址或关键库存信息。后续如果真实日志仍有超长，再增加“保留事实的压缩重写”阶段。

## 4. 失败安全

- 不能确认指代对象：澄清，不猜；
- 低置信度：保留原有检索回退路径；
- 上下文预算达到上限：停止继续注入子块，不清空已获得事实；
- 工具被误调用：工具自身限制返回量；
- 线索收集后续接入时：一轮最多推进城市或电话其中一项。

## 5. 验证场景

- “这个太贵了”承接上一轮唯一车系；
- “这款怎么样”在多车系历史下只澄清不猜；
- “还有吗那款车”使用历史实体重写检索；
- “最便宜的 SUV”“省油一点的”进入偏好指导；
- 品牌级查询不列库存清单；
- 多车系细节查询不超过整轮子块预算；
- 库存工具返回不超过配置上限。
